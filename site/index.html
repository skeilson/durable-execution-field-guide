async and await: waiting for the outside world

Charging a card or calling another service takes time. Code that waits for something like that is marked async, and each place it waits says await:

async function checkout() {
  await inventory.reserve("order-1", "SKU-42");   // wait for the warehouse to answer
  await bank.charge("order-1", 4999);             // then wait for the bank
  await shipping.ship("order-1", "123 Main St");  // then wait for shipping
}

Read await as "do this, and wait until it's finished before the next line." That gives you the most important idea in this course: a program is a list of steps, done in order, each one waiting on something outside.

Errors

When something goes wrong, code throws an error. Other code can catch it:

try {
  await bank.charge("order-1", 4999);
} catch (err) {
  console.log("The charge failed: " + err.message);
}

console.log(...) just prints a line in the terminal.

The pattern you'll see everywhere

Here's a real snippet from Module 3. With the above, you can read it:

"Run a step called charge card. The step is: charge this order's amount at the bank. Wait for it to finish, and call the result paymentId." ctx is the durable execution engine. Module 2 explains what it's doing behind the scenes.

An online order, step by step

When you buy something online, a program on the store's side does roughly this:

flowchart LR
    A[Reserve the item<br/>in the warehouse] --> B[Charge the<br/>customer's card] --> C[Ship it]

Each box is a step, and each step talks to a different system: the warehouse's inventory system, a payment provider like Stripe, a shipping carrier. Written as code it's three lines:

await inventory.reserve(orderId, "SKU-42");
await bank.charge(orderId, 4999);
await shipping.ship(orderId, "123 Main St, Bozeman MT");

Side effects

Each of those steps changes something outside the program: an item is held, money moves, a box gets a label. These changes are called side effects, and they're the whole point. A checkout that didn't charge or ship anything would be useless.

Side effects have one property that makes everything in this course hard:

A side effect can't be taken back just by stopping the program.

If the program stops after the charge, the money has still moved. Undoing it takes another side effect (a refund), which is another step that can also fail.

Inside the program vs. outside

Inside the program (memory)Outside the program (the world)
Variables like orderId, paymentIdThe bank's record of the charge
Which line it's currently onThe warehouse's reservation
Gone the instant the program stopsStays forever

That mismatch is the root of the problem. The knowledge of what happened lives in memory, which is fragile. The consequences live outside, which is permanent. When the program dies, it forgets what it did but the world doesn't.

Real processes are longer

Three steps is a toy example. Real ones look like:

  • Subscription billing: charge → wait 30 days → charge again → if it fails, retry in 3 days → email → retry in 7 days → cancel
  • Loan application: collect documents → credit check → wait for an underwriter's approval (could be days) → sign → fund
  • AI agent: ask the model → call a tool → ask the model again → call another tool → … (dozens of steps, each costing money)

More steps, longer waits and more outside systems mean more places to fail halfway.

Things that stop programs

Programs stop unexpectedly all the time, and usually not because of a bug in the program itself:

  • Deploys. Shipping new code means stopping the old version. Many companies deploy dozens of times a day.
  • Crashes. Running out of memory, a bug in a library, a bad input.
  • Infrastructure. A server is replaced, a cloud zone has an outage, a container platform like Kubernetes moves the program to another machine.
  • Timeouts. Serverless platforms (AWS Lambda and others) kill any program that runs longer than a limit, often 15 minutes.

At scale this isn't rare. A company processing a million orders a day will have orders in flight every time any of the above happens.

Can't we just run it again?

The obvious fix is to rerun the checkout. But the program has no memory of the previous run. It starts from line one:

What we'd really want is for the rerun to know how far the last run got and pick up from there. Hold that thought: it's the core idea of Module 2.

The two bad options

When a multi-step process fails halfway, without special tooling you get to choose between:

OptionRisk
Rerun from the startSteps that already happened happen again (double charge, two shipments, duplicate emails)

Neither is acceptable, and that's why companies build elaborate machinery to cope (lesson 1.5).

Support angle "We had an outage and now some orders are stuck" and "some customers got charged twice" are among the most common tickets in this product category. They're usually the same root cause, partial failure, handled in one of the two bad ways above.

This lesson covers the single most important idea in the course. It's subtle, so take it slowly.

Asking and answering are separate events

When our program charges a card, two separate messages travel over the network:

  1. The request: "please charge $49.99"
  2. The response: "done, payment id pay_123"

Either one can be lost: a network blip, an overloaded server, a timeout. And the program can't tell which was lost.

    participant B as Bank
    rect rgb(240, 248, 240)

    Note over P: ⏱ timeout

From the program's point of view, both cases look identical: it sent a request and got a timeout. But in case A nothing happened, and in case B the customer was charged.

This is called an ambiguous failure. An error after sending a request doesn't mean the request failed. It means you don't know.

Why you can't just check

"Ask the bank whether it charged" sounds like a fix. But that question is also a request over the same network, and its answer can get lost too. You can reduce the uncertainty, but you can't build a program that is always certain about what happened on the other side of a network.

Computer scientists proved this decades ago (look up the "Two Generals' Problem" if you're curious). The practical takeaway is simpler:

Any step that talks to another system can fail in a way where you can't tell whether it happened.

In the demo

Scenario 3 of npm run m1 makes the bank lose its reply on purpose. The program prints an error, and the ledger shows the customer was charged. If you were the support engineer and the customer's logs said "charge failed," you'd tell them they weren't charged, and you'd be wrong.

Support angle Never conclude "the step didn't happen" from an error message alone. Check the system of record: the payment provider's dashboard, the warehouse's database, the email provider's logs. This habit will save you from giving customers confidently wrong answers.

Where this leaves us

Ambiguous failures mean that even a perfect record of "what our program did" can't tell us what the outside world did. Durable execution helps a lot here, but it can't eliminate ambiguity on its own. It needs help from the outside systems, through idempotency keys (lesson 2.5). Keep this lesson in mind; it comes back in every module.

Retries are necessary

Most failures between systems are transient: they go away if you wait a moment and try again. A server was restarting, a network link hiccuped, a service was briefly overloaded. So programs retry:

for (let attempt = 1; attempt <= 3; attempt++) {
  try {
    return await bank.charge(orderId, 4999);
  } catch (err) {
    // wait a bit, then loop around and try again
  }
}

Scenario 4a of the demo shows this working: the bank returns 503 Service Unavailable once, the retry succeeds, and the customer is charged exactly once.

Retries meet ambiguity

Now combine retries with lesson 1.3. The bank charges the card, the reply is lost, the program sees a timeout and retries:

The table to remember

Kind of failureDid the side effect happen?Is retrying safe?
Request never arrived (503, connection refused)No✅ Yes
Response lost (timeout after sending)Maybe⚠️ Only if the other side can spot duplicates
Permanent error (card declined, invalid address)No❌ Pointless: it will fail every time

Two things follow:

  1. Retries need a way to make repeats harmless. That's idempotency (lesson 2.5).
  2. Retries need to know when to give up. Retrying a declined card forever just annoys the bank. That's the distinction between transient and permanent errors (lesson 2.6).

Other ways retries go wrong

Even when retries are safe, they cause trouble at scale:

  • Retry storms. A service goes down, every caller retries at once, and the flood keeps it down. The fix is backoff: wait longer after each failure (1s, 2s, 4s, 8s…), plus a little randomness so callers don't retry in lockstep.
  • Retrying forever. A step that can never succeed, retried endlessly, quietly blocks the order behind it. Nobody notices until a customer complains. This is a classic "stuck workflow" ticket (Module 6).

Support angle When a customer says "the retries made it worse," the questions to ask are: was the failure ambiguous (a timeout)? Was the call idempotent? Was there backoff? Those three usually find the cause.

Partial failure isn't new. Before durable execution platforms existed, teams solved it with a toolkit of patterns. You'll meet these in customer conversations, often because a customer is migrating away from them, so it's worth knowing what they are and why they hurt.

The status column

Store each order's progress in a database:

order_idstatusupdated_at
order-1001CHARGED10:04:12
order-1002SHIPPED10:04:15

After every step, update the status. After a crash, read the status and resume. It works, but every process now needs its own table, every step needs an extra database write, and the logic for "resume from status X" is hand-written for every process and every status.

Queues

Put each step's work in a message queue (RabbitMQ, SQS, Kafka). A worker takes a message, does the step, and puts the next step's message on the queue. If the worker crashes, the message goes back on the queue for another worker.

It's resilient, but the process is now scattered across many small handlers. Nobody can read the whole flow in one place, and "where is order 1001 right now?" becomes a detective story.

The sweeper (cron job)

A scheduled job runs every few minutes, finds records stuck in some status for "too long," and kicks them. Every team writes one, and every team has an incident where the sweeper and the original process both acted on the same order at once.

Hand-written sagas

When step 3 fails permanently, steps 1 and 2 must be undone: release the inventory, refund the charge. Teams write this "compensation" logic by hand, and it has its own partial failures (what if the refund fails?).

The promise of durable execution

Durable execution makes one bold claim:

Write the process as ordinary, top-to-bottom code. The platform makes it survive crashes, restarts and deploys.

No status tables, no sweepers, no hand-built resume logic. The process reads like the three-line checkout from lesson 1.1, and it behaves as if it never crashed.

Module 2 shows how that's possible by building it yourself.

Support angle Customers migrating from queues and status tables often carry old assumptions with them, like "we need our own retry loop around this call" (now you have two layers of retries) or "we'll track status in our database too" (now there are two sources of truth that can disagree). Spotting these is a big part of onboarding support.

Module 1 ended with a wish: after a crash, the rerun should know how far the last run got. Durable execution grants that wish with one simple rule.

Write it down before moving on

Every time a step finishes, write down its result. After a crash, run the code again from the top, and for every step that's already written down, use the recorded result instead of doing the step again.

That's it. Everything else in this course is detail on top of that sentence.

The written record is called the journal. Temporal calls it the event history; same idea. Using the journal to fast-forward through finished steps is called replay.

What v1 does

Engine v1 does exactly one thing: after each step finishes, it appends the step's name and result to a file.

async step(name, fn) {
  const result = await fn();                       // do the work
  this.journal.entries.push({ step: name, result }); // NEW: write it down
  saveJournal(this.file, this.journal);              // to disk, before moving on
  return result;
}

After a full run, the journal for order-22a looks like this (it's a plain file you can open: .runtime/journals/v1/order-22a.json):

{
  "workflowId": "order-22a",
  "status": "completed",
  "entries": [
    { "step": "reserve inventory", "result": "res_order-22a" },
    { "step": "charge card",       "result": "pay_order-22a" },
    { "step": "ship order",        "result": "trk_order-22a" }
  ]
}

Why "before moving on" matters

The journal write happens after the step finishes and before the next step starts. That ordering is the whole guarantee: if a step's result is in the journal, the step definitely happened. (The reverse, "if it happened, it's in the journal," is not guaranteed. Lesson 2.4 is about that.)

One more detail: the engine writes to a temporary file and then renames it. A rename is all-or-nothing, so a crash in the middle of saving can't leave a half-written journal. Real engines are fussy about this kind of thing, because a corrupted journal is far worse than a crash.

The catch

v1 writes a journal but never reads it. So after a crash, the rerun starts from the top and charges again. The journal knew the charge happened, and nobody asked it.

What's new in v2

v2 loads the journal on startup and keeps a position counter. Every time the code asks for a step, the engine checks whether the journal already has an entry at that position:

async step(name, fn) {
  const recorded = this.journal.entries[this.position];
  if (recorded) {                    // NEW: already done in an earlier run?
    this.position++;
    return recorded.result;          // hand back the old result, skip the work
  }
  const result = await fn();         // otherwise, do it for real
  this.journal.entries.push({ step: name, result });
  saveJournal(this.file, this.journal);
  this.position++;
  return result;
}

Replay is fast

Replaying a step is just reading a value, with no network call and no waiting. A workflow with 500 completed steps can replay in milliseconds. That's what makes it practical to "run from the top" every time.

Two consequences

1. Code outside steps runs every time. Anything not wrapped in ctx.step(...), like a console.log, runs on every replay. That's harmless for logging (Restate even hides log lines during replay to cut noise). It's very harmful for side effects: a charge that isn't inside a step happens on every replay. Rule: every side effect goes inside a step.

2. The journal is matched by position. "Entry #1 is the answer to the second step the code asks for." That only works if the code asks for the same steps in the same order every time. Lesson 2.7 shows what happens when it doesn't.

Support angle When a customer says "my workflow ran the whole thing again after a restart," check two things: are their side effects actually inside durable steps, and are they seeing replay (normal, fast, no side effects) or genuine re-execution? Restate's logs say Replaying invocation, and Temporal's Web UI shows the history being replayed. Explaining replay is one of the most common onboarding conversations.

                               // ← 💥 what if we crash HERE?
this.journal.entries.push(…);  // 2. we record that it happened

Between "the side effect happened" and "we recorded it" there is a window. It might be a millisecond, but at a million orders a day it will be hit.

If the process dies in that window, the journal has no record of the charge. On restart, the engine reaches the charge step, finds nothing at that position, and executes it again.

No engine can close it alone

You might think a cleverer engine could fix this: record "about to charge" first, then charge, then record "charged." But after a crash between those, all the engine knows is "I was about to charge." Did the charge go through? That's the ambiguous failure from lesson 1.3 again. The engine's view of the world stops at its own process.

So every durable execution engine, including Restate and Temporal, makes this promise:

Each step's work runs at least once. Once a step's result is recorded, it's never re-executed.

That's called at-least-once execution. The honest summary is "almost always once, occasionally twice, never zero times."

Why at-least-once is still a huge improvement

Without durable executionWith durable execution
Crash between stepsRerun repeats every finished stepFinished steps are replayed, never repeated
Crash inside a stepRerun repeats every finished stepOnly the one interrupted step repeats

The engine shrinks the danger from "everything might repeat" to "the one step that was in flight might repeat." Lesson 2.5 makes that one repeat harmless.

Support angle "But you guarantee exactly-once!" is a common customer misunderstanding, and marketing pages for this category don't always help. The precise statement: the workflow makes progress exactly once (each step's result is recorded once and reused), but each step's side effect is at-least-once. A word worth learning

Idempotent (eye-dem-POH-tent) describes an operation you can do twice with the same effect as doing it once.

  • Pressing an elevator's call button: idempotent. Pressing it five times doesn't summon five elevators.
  • Setting a thermostat to 70°: idempotent.
  • "Add $50 to the account": not idempotent. Do it twice and it's $100.
  • "Charge this card $49.99": not idempotent, unless…

Idempotency keys

Most payment APIs (Stripe, Adyen, PayPal and many others) let you attach a unique idempotency key to a request. The provider remembers keys it has seen. If the same key arrives again, it doesn't charge again: it returns the result of the original request.

sequenceDiagram
    participant E as Engine
    participant B as Bank
    E->>B: charge $49.99, key = order-25/charge card
    Note over B: 💳 charged, remembers key
    Note over E: 💥 crash before journaling
    E->>B: charge $49.99, key = order-25/charge card (retry)
    Note over B: seen this key → no new charge
    B-->>E: pay_order-25 (the original result)

The step ran twice; the customer was charged once.

Where does the key come from?

The key must be the same every time this step runs for this order, and different for everything else. Engine v3 builds it from two things that never change:

const idempotencyKey = `${this.workflowId}/${name}`;  // "order-25/charge card"

A random key or a timestamp would be useless: the retry would get a different key, and the bank would treat it as a new charge.

The two halves

This is the most important pairing in the course:

Durable execution guarantees each step's result is recorded once and the workflow never loses its place. Idempotency guarantees that the occasional repeated step doesn't repeat its effect. Together they give you effectively exactly once.

Neither half works alone:

No idempotency keyWith idempotency key
Plain codeDuplicates on every rerunRerunning is safe, but the process still forgets where it was
Durable executionRare duplicates (crash mid-step)✅ Effectively once

What if the outside system doesn't support keys?

Not every API does. The options, roughly in order of preference:

  1. Check before acting. "Has an order with this id already been shipped?" Only works if the check is reliable.
  2. Make the action naturally idempotent. "Set the status to shipped" instead of "add a shipment."
  3. Put a deduplication table in front of it. Your own record of keys you've used.
  4. Accept the rare duplicate and handle it afterwards, like refunding duplicate charges found by a nightly reconciliation job.

Moving retries into the engine

In Module 1, retry logic was written by hand inside the checkout. Engine v4 moves it into ctx.step, so every step gets retries without the workflow code changing at all:

for (let attempt = 1; ; attempt++) {
  try {
    result = await fn({ idempotencyKey, attempt });
    break;                                          // success: stop retrying
  } catch (err) {
    if (err instanceof PermanentError) throw …;     // never retry these
    if (attempt >= retry.maxAttempts) throw …;      // give up eventually
    await sleep(retry.initialDelayMs * 2 ** (attempt - 1));  // 200ms, 400ms, 800ms…
  }
}

Three experiments

A) The bank is down for a moment. Two 503 errors, then success. The engine waits 200ms, then 400ms, then succeeds. The workflow never noticed.

B) The lost response. The bank charges, the reply is lost, the engine retries. In Module 1 this charged twice. Now the retry carries the same idempotency key (it's derived from the order id and step name, which don't change between attempts), so the bank ignores the duplicate. Retries are only safe because of idempotency.

C) The card is declined. Retrying can't change the answer, so v4 stops immediately and marks the workflow failed.

Transient vs. permanent

The engine has to decide, for every error, whether to retry. That's a decision only the developer can make, because only they know what each error means. Every engine gives them a way to say "this one is final":

A step that can never succeed (a bug, a bad input, a wrong API key) but throws an ordinary error gets retried over and over. The assumption replay makes

Replay matches journal entries to steps by position: "entry #2 is the answer to the third step the code asks for." That only works if, given the same journal, the code asks for the same steps in the same order every time it runs. Code with that property is called deterministic.

Ordinary code is usually deterministic. Two things break it.

Break #1: decisions that change between runs

A promotion gives half of all orders free gift wrap:

await ctx.step("charge card", …);
if (Math.random() < 0.5) {               // ✘ a coin flip OUTSIDE any step
  await ctx.step("gift wrap", …);
}
await ctx.step("ship order", …);
RunCoinCode asks for, in orderJournal
1st0.1 → wrapreserve, charge, gift wrap, 💥#0 reserve, #1 charge, #2 gift wrap
2nd0.9 → no wrapreserve ↺, charge ↺, ship order#2 is "gift wrap"!

On replay the code asks for "ship order" at position #2, but the journal says position #2 was "gift wrap." The engine has two bad options: return gift wrap's result to the ship step (nonsense), or execute ship and leave the journal inconsistent. v5 does neither. It stops with a NonDeterminismError. Failing loudly is the safe choice: the journal is untouched, and once the code is fixed the workflow can continue.

The fix: make the decision inside a step, so it's journaled:

const roll = await ctx.random("gift wrap roll");   // ✔ recorded; replay gets the same number
if (roll < 0.5) { … }

Anything that can give a different answer on a different run must be journaled:

Temporal takes a stricter approach than Restate here: workflow code runs in a sandbox that swaps out Math.random and Date for deterministic versions and blocks things like direct network calls. Restate gives you deterministic helpers on ctx and expects you to use them. Modules 3 and 4 go into this.

Break #2: changing the code under a running workflow

An order crashes after charging. Before it restarts, a developer deploys a new feature, a confirmation email after reserving inventory:

await ctx.step("reserve inventory", …);
await ctx.step("send confirmation email", …);   // NEW
await ctx.step("charge card", …);

The order replays on the new code. Position #1 in its journal is "charge card", but the code asks for "send confirmation email." Non-determinism again.

Here's the twist that makes this confusing in real life: whether it breaks depends on how far each workflow had gotten. An order that hadn't reached position #1 yet is fine. An order already past it breaks. A deploy can break 3% of in-flight workflows and leave the rest working, which looks random to the customer.

Every serious engine has tools for changing code safely while workflows are running. They differ a lot between Restate and Temporal, and they're among the most important things a support engineer in this space must understand. Module 7 is largely about them.

A timer is just another step

Engine v6 adds ctx.sleep(name, ms). The trick is to journal when to wake up, not how long to wait:

async sleep(name, ms) {
  const wakeAt = await this.step(`timer: ${name}`, async () => Date.now() + ms);  // journaled once
  const remaining = wakeAt - Date.now();
  if (remaining > 0) await realSleep(remaining);   // on replay: only what's left
}

What real engines add: nobody needs to stay awake

The mini engine still keeps a process running during the wait. That's fine for 6 seconds and absurd for 30 days.

Restate and Temporal move the timer to the server. While a workflow sleeps, your code doesn't need to be running at all. Your service can be scaled to zero, redeployed or moved. When the timer fires, the server wakes the workflow up and replays it to the line after the sleep.

sequenceDiagram
    participant Code as Your service

    Note over Server: ⏰ holds the timer
    Server->>Code: 30 days later: wake up
    Note over Code: replay to the line<br/>after sleep, continue

This is called suspension, and it's what makes durable execution practical for long-running processes. It's also why incident 6.1 works: the Restate server held the warehouse timer while the service was dead.

If you can explain these to someone else, you understand durable execution:

  1. Journal: each step's result is written down before moving on.
  2. Replay: after a crash, rerun from the top, reusing recorded results.
  3. At-least-once: a step interrupted mid-flight runs again. No engine can avoid that alone.
  4. Idempotency: stable keys make that repeat harmless. Engine plus idempotency gives effectively once.
  5. Retries: transient errors are retried with backoff; terminal errors stop. Default is to keep retrying.
  6. Determinism: replayed code must ask for the same steps in the same order. Randomness, time and changing code break it.
  7. Durable timers: journal the wake-up time; real servers hold the timer so nothing has to stay running.

Restate pushes work to your service

In your mini engine, your code called the engine. Restate is the other way around: the Restate server calls your service when there's work to do. This is the "push" model from lesson 2.9.

What happens on one request:

  1. A client sends POST /Orders/checkout to Restate.
  2. Restate records the request as an invocation with a new id (inv_…) and an empty journal.
  3. Restate calls your service's checkout handler, sending along any journal it already has.
  4. Each time the handler does something through ctx (a ctx.run, a call, a sleep), the SDK reports it to Restate, which adds it to the journal.
  5. When the handler returns, Restate records the result and answers the client.

If the service crashes at step 4, Restate notices the connection broke and calls the handler again, this time sending the journal so far. The SDK replays from it, exactly like engine v2.

ctx.run(name, fn) is Restate's version of your ctx.step: run fn once, record its result in the journal, and on replay return the recorded result without running fn again. The name is for humans: it shows up in the CLI and UI.

The rules of ctx.run

These come straight from Module 2:

  1. Every side effect goes in a ctx.run. Calls to databases, APIs and payment providers, plus anything else that touches the outside world. A side effect outside ctx.run repeats on every replay.
  2. The result must be serializable (convertible to JSON), because it's stored in the journal. Return the data you need, not a database connection or a class instance.
  3. It's at-least-once. If the service dies while fn is running, fn runs again. Pass idempotency keys to outside systems (lesson 2.5).
  4. Don't use ctx inside ctx.run. A ctx.run is one side effect, not a mini workflow.

Compare with Module 1: a plain program that sends an email and then crashes has no idea whether the email went out. Here, the send is in the journal. On replay it isn't sent again, and Restate guarantees delivery.

Idempotency at the front door

Lesson 2.5 covered idempotency keys for calls out to other systems. Restate also accepts them on calls coming in. Send the header idempotency-key with any request:

curl localhost:8080/Orders/checkout \
  -H 'idempotency-key: order-34' \
  --json '{"orderId":"order-34", …}'

If the same key arrives again (a double-clicked button, a client retrying after a timeout), Restate doesn't start a second invocation:

  • If the first is still running, the second request attaches to it and gets the same result when it finishes.
  • If the first already finished, Restate returns its stored result.
  • With /send, the response says "status": "PreviouslyAccepted" instead of "Accepted".

Restate remembers keys for a retention period (1 day by default, configurable per service or handler).

The rule

Restate sorts every error into one of two kinds, using one simple rule:

ThrownRestate does
TerminalErrorStops. The invocation fails, and the error goes back to the caller. Never retried.
Anything elseRetries with growing delays, according to the retry policy

Retrying is the default because it's the safe choice for a system that must not lose work. If the developer doesn't say an error is final, Restate assumes it might go away.

A) Transient failure: retried automatically

The bank returns 503 four times, then recovers. Checkout's code has no retry logic, yet the order completes with one charge. While it's failing, the lesson shows the payment invocation:

  return await bank.charge(…);

  if (err instanceof PermanentError) throw new restate.TerminalError(`Card declined for ${orderId}`);

The developer translates "declined" into a TerminalError. It fails Payments/charge, and because Orders called Payments with serviceClient, the error propagates to Orders, then to the client. The customer gets an answer immediately instead of a request that hangs while Restate retries something hopeless.

The stock reserved before the charge stays reserved. Lesson 3.10 shows how to undo it.

Suspension

When a handler is waiting on something that will take a while (a timer, a call to another service, a promise from lesson 3.8), the Restate SDK can suspend the invocation:

  1. The service tells Restate "I'm waiting on entry #1" and ends the request. The process is free.
  2. Restate holds the timer.
  3. When the timer fires, Restate calls the handler again with the journal. The SDK replays to the line after sleep and continues.
Status:   suspended
Journal:
 [1]: Sleep command  wait until reminder is due
   └ until 13:27:06 (in 10s)
Last Event:
  Suspended after entry #1
    waiting on: Sleep [wait until reminder is due] (entry #1) or cancel

This is what lets a Restate handler wait 30 days, or run on a serverless platform that kills functions after 15 minutes.

Restate doesn't suspend instantly. By default the SDK keeps the request open for about a minute (the inactivity timeout) in case the wait is short, which saves a round trip. The reminders service sets it to 1 second so you can watch suspension happen:

The problem they solve

A shopping cart needs to be stored somewhere and updated safely. Normally that means a database, plus careful code so two simultaneous "add to cart" requests don't overwrite each other: both read [mug], both write [mug, X], and one item is lost. That bug is called a race condition, and it's notoriously hard to find.

A virtual object

export const cart = restate.object({
  name: "Cart",
  handlers: {
    add: async (ctx: restate.ObjectContext, item) => {
      const items = (await ctx.get<CartItem[]>("items")) ?? [];
      items.push(item);
      ctx.set("items", items);
      return items.length;
    },
    view: restate.handlers.object.shared(async (ctx: restate.ObjectSharedContext) => {
      const items = (await ctx.get<CartItem[]>("items")) ?? [];
      return { customer: ctx.key, items };
    }),
  },
});

A virtual object is a service with a key. Every key (here, a customer id) is its own independent object:

  • State. ctx.get and ctx.set read and write key/value state that Restate stores for that key. No database to set up. State changes are journaled along with everything else, so they're never half-applied.
  • One at a time per key. Restate runs at most one exclusive handler (the default kind) per key at a time. Others for the same key wait in line. Different keys run in parallel.
  • Shared handlers (handlers.object.shared) can only read, and run at any time without waiting in line.

The key is part of the URL:

curl localhost:8080/Cart/dana/add --json '{"sku":"MUG","priceCents":1500}'
curl -X POST localhost:8080/Cart/dana/view
npx restate state get Cart dana

The queue in action

The lesson slows add down to 2 seconds and sends three at once:

dana +PEN done after 2.0s
dana +INK done after 4.0s     ← waited for dana's first add
sam  +HAT done after 2.0s     ← different key, ran in parallel

No locks and no transactions, and the race condition can't happen.

A process that needs a human

A customer returns a broken item. Someone on the support team must approve the refund, which might happen in five minutes or next Tuesday. The process has to wait for an event from outside, and other people need to check its progress while it waits.

A Restate workflow

export const returns = restate.workflow({
  name: "Returns",
  handlers: {
    run: async (ctx: restate.WorkflowContext, req) => {
      ctx.set("status", "waiting for approval");
      const decision = await ctx.promise<Decision>("decision");   // wait…
      if (!decision.approved) { … return { refunded: false }; }
      await ctx.run("refund", () => bank.refund(req.orderId, req.amountCents));
      ctx.set("status", "refunded");
      return { refunded: true };
    },

    decide: async (ctx: restate.WorkflowSharedContext, decision) => {
      await ctx.promise<Decision>("decision").resolve(decision);  // …until this happens
    },

    status: async (ctx: restate.WorkflowSharedContext) => ctx.get("status"),
  },
});

A workflow is a virtual object with special rules:

  • The run handler executes exactly once per key (here, per return id). Calling run again for the same id is refused with HTTP 409.
  • Other handlers (decide, status) can be called while run is in progress, as many times as you like.
  • A durable promise (ctx.promise("decision")) is a named value run can wait for, which another handler completes. It's stored in Restate, so it survives anything.
curl localhost:8080/Returns/return-38/run/send --json '{"orderId":"order-38", …}'
curl -X POST localhost:8080/Returns/return-38/status        # "waiting for approval"
curl localhost:8080/Returns/return-38/decide --json '{"approved":true,"by":"sam"}'
curl -X POST localhost:8080/Returns/return-38/status        # "refunded"

Webhooks

Many external systems don't answer immediately. You ask a payment provider to start a payment, and minutes later they call you (a webhook) with the result. Without durable execution you'd need to store "order X is waiting for payment" in a database, build a webhook endpoint that looks it up, and handle the provider calling back before you've finished saving.

Awakeables

An awakeable is a durable "call me back" ticket that any service can create:

const { id, promise } = ctx.awakeable<PaymentResult>();

await ctx.run("ask provider to start payment", () =>
  provider.startPayment({ ...req, callbackId: id }));     // hand them the ticket

const result = await promise;                            // suspend until called back

The outside world completes it through Restate's HTTP API:

curl localhost:8080/restate/awakeables/<id>/resolve --json '{"status":"paid","providerRef":"prov_8812"}'
# or, on failure:
curl localhost:8080/restate/awakeables/<id>/reject -H 'content-type: text/plain' -d 'card expired'

In a real integration, your webhook endpoint receives the provider's callback, reads the awakeable id from it (you passed it as metadata), and calls resolve. A Restate handler can also do it with ctx.resolveAwakeable(id, value).

The leftover reservation

In lessons 2.6 and 3.5, a declined card left inventory reserved for an order that would never complete. In general: when a later step fails for good, earlier steps may need undoing. Databases solve this with transactions, but a transaction can't span a warehouse, a bank and a shipping carrier. The pattern for this is called a saga.

The scenario

A customer places an order and types their address as "Nowhere". Nothing checks the address at checkout, so the order starts normally: the stock is reserved and the card is charged. Only at the last step does the carrier look at the address, find no street number, and refuse it.

That refusal is permanent: no amount of retrying turns "Nowhere" into a deliverable address. (A carrier outage would be different: that's transient, and should be retried, not undone.) The customer has now paid for an order that can never ship, with stock held for it. Both need undoing.

The pattern

  1. After each step succeeds, remember how to undo it (its compensation).
  2. If a step fails with a TerminalError, run the compensations in reverse order.
  3. Then report the failure.
const compensations = [];
try {
  await ctx.run("reserve inventory", () => inventory.reserve(…));
  compensations.push(() => ctx.run("release inventory", () => inventory.release(…)));

  await ctx.serviceClient(payments).charge({ … });
  compensations.push(() => ctx.serviceClient(payments).refund({ … }));

  await ctx.run("ship order", () => shipping.ship(…));   // ← carrier rejects the address
} catch (err) {
  if (!(err instanceof restate.TerminalError)) throw err;  // transient: let Restate retry
  for (const undo of compensations.reverse()) await undo();
  throw err;
}

  bank      charge    $49.99
  bank      refund    $49.99
  inventory release   SKU-42

Why durable execution makes sagas practical

Hand-written sagas (lesson 1.5) are fragile: what if the process crashes after the refund but before releasing the inventory? Here, the compensations are durable steps too. A crash halfway through undoing resumes halfway through undoing. The compensation list doesn't even need saving, because replay rebuilds it: replaying the steps re-runs the compensations.push(…) lines.

Design rules

RuleWhy
Only terminal errors trigger compensationA transient error should be retried, not undone
Compensations must be retryable and idempotentThey're at-least-once like every step, and they shouldn't fail permanently. A refund must eventually succeed.
Compensate in reverse orderUndo the newest change first, like unstacking plates
Not everything can be undoneAn email can't be unsent. Send a correction, or put irreversible steps last.

There's a subtle variant worth knowing: some teams register the compensation before the step runs, because a step that failed ambiguously (lesson 1.3) might have partly happened. That's only safe when the compensation is harmless if nothing happened, such as refunding a charge that doesn't exist.

Support angle Customers ask "does Restate roll back automatically?" No: Restate guarantees your compensation code runs reliably, but you write the compensations. When a saga ticket comes in ("we refunded but didn't release stock"), check whether the failing step threw a TerminalError (only those trigger the catch) and whether every completed step registered its undo.

Restate exposes its internals as SQL tables. A few queries cover most investigations:

  const tracking = await acts.shipOrder(order.orderId, order.address);
  return { orderId: order.orderId, reservation, payment, tracking };

Compare it with Restate's orders.ts. It's the same shape: top-to-bottom code, durable steps, a durable timer. The differences:

  • Side effects are activity calls (acts.chargeCard(…)) instead of ctx.run(…) blocks.
  • There's no ctx. Workflow functions use helpers imported from @temporalio/workflow.
  • Every activity call must say how long one attempt may take (startToCloseTimeout). Temporal requires a timeout so it knows when to give up on an attempt and retry it.

Scaling and routing

  • More workers = more throughput. Run more copies of the worker on the same task queue; they share the work. No load balancer needed.
  • Task queues route work. Activities can run on a different queue from their workflow, for example GPU workers for an AI step or workers inside a specific network for a database call.
  • A task queue exists as soon as something uses its name. A typo doesn't produce an error: it creates a different, empty queue that no worker polls.

Defining and handling them

export const addItem = defineSignal<[CartItem]>("addItem");
export const viewCart = defineQuery<{ items: CartItem[]; totalCents: number }>("viewCart");
export const checkoutCart = defineUpdate<string, [string]>("checkoutCart");

export async function cart(customer: string, items: CartItem[] = []) {
  setHandler(addItem, (item) => { items.push(item); });
  setHandler(viewCart, () => ({ items, totalCents: … }));
  setHandler(checkoutCart, async (address) => {
      const id = …;
      await acts.reserveInventory(id, …);     // the update does real work
      orderId = id;
      checkedOut = true;                      // only now is checkout finished
      return id;
    },
    { validator: (address) => { if (items.length === 0) throw new Error("Cart is empty"); } });

  await condition(() => checkedOut);         // wait for checkout to FINISH
  await condition(allHandlersFinished);      // never end with a handler still running
  return orderId;
}

Handlers update ordinary variables in the workflow. Because signals and updates are recorded in the history, replaying the history replays the same handler calls in the same order, so the variables always come out the same. Queries only read and leave no trace.

An update's validator runs before the update is accepted. Rejecting there gives the caller an error and leaves no trace in the history.

A trap: ending while a handler is still running

An earlier version of this course had a bug worth learning from. The checkout handler set orderId before reserving the stock, and the workflow waited on orderId !== undefined. So as soon as checkout started, the main function saw an order id, returned, and the workflow completed, while the update handler was still waiting for its activity. Temporal then failed the update, and the caller saw only Workflow Update failed.

Two rules prevent it:

  • Mark work as done after it's done (checkedOut = true comes after the activity).
  • Before a workflow returns or continues as new, wait for allHandlersFinished. The SDK also logs a warning when a workflow ends with handlers still running. Look for it in worker logs.

History limits and continue-as-new

Every event in a workflow's history is stored and replayed. Histories can't grow forever: Temporal warns as a history gets large, and terminates a workflow whose history passes a hard limit (by default around 50,000 events or 50 MB). A long-lived entity workflow like a cart, receiving signals for months, will eventually hit it.

The fix is continue-as-new: the workflow ends its current run and immediately starts a new run, with the same workflow id, a fresh empty history, and whatever state you pass along:

await condition(() => orderId !== undefined || events >= 100);
if (orderId === undefined) {
  await continueAsNew<typeof cart>(customer, items);   // new run, same id, carry the items
}

In the lesson, 105 signals push the cart past 100 events, and the list shows two runs:

Status          WorkflowId  Type  …
ContinuedAsNew  cart-lee    cart
Running         cart-lee    cart

The shop uses 100 events so you can see it happen. Real workflows use thousands, or check workflowInfo().continueAsNewSuggested, which the server sets when the history is getting large.

The saga pattern is the same in Temporal as in Restate (lesson 3.10): remember how to undo each completed step, and when a later step fails for good, undo in reverse.

export async function orderSaga(order: Order) {
  const compensations: Array<() => Promise<unknown>> = [];
  try {
    await acts.reserveInventory(order.orderId, order.sku);
    compensations.push(() => acts.releaseInventory(order.orderId, order.sku));

    await acts.chargeCard(order.orderId, order.amountCents);
    compensations.push(() => acts.refund(order.orderId, order.amountCents));

    await acts.shipOrder(order.orderId, order.address);   // ← non-retryable: address rejected
    return { orderId: order.orderId, status: "shipped" };
  } catch (err) {
    for (const undo of compensations.reverse()) await undo();
    throw ApplicationFailure.nonRetryable(`Order ${order.orderId} failed and was rolled back`, "OrderFailed");
  }
}

Lesson 2.7 showed two ways to break replay: decisions that change between runs, and code that changes under a running workflow. Temporal handles the first with a sandbox and gives you patching and replay testing for the second.

The sandbox

The TypeScript SDK bundles your workflow code and runs it in an isolated environment inside the worker:

Code changes: the history must still line up

The sandbox can't save you from changing the code. workflows-changed.ts adds an email between reserve and charge:

await acts.reserveInventory(…);
await acts.sendEmail(order.orderId, "We're preparing your gift");   // NEW
await acts.chargeCard(…);

A workflow that started on the old code has a history saying "after reserve, charge was scheduled." Replaying it on the new code, the worker schedules an email instead, and Temporal stops with a non-determinism error. The workflow task fails and is retried, and the workflow sits Running until a compatible version of the code is deployed.

The two architectural differences that matter most

1. Push vs. pull. Restate calls your services; Temporal's workers poll for work. This decides how outages look (loud errors vs. silent queues), how you deploy (any HTTP endpoint or serverless function vs. long-running workers), and what networking is needed.

2. Where side effects live. Restate puts them inline (ctx.run blocks inside one handler). Temporal puts them in separate functions (activities), called from a sandboxed workflow. Restate code reads like ordinary code; Temporal's separation makes the boundary between orchestration and side effects explicit and enforced.

Quick translation practice

As a support engineer at either company, you'll be asked "why you and not them?" by prospects, and "should we migrate?" by customers. The honest answer is always "it depends," followed by what it depends on.

Restate tends to fit when…

  • The team wants minimal infrastructure: one binary, or a managed service, plus their existing HTTP services
  • Code runs on serverless platforms (Lambda, Cloudflare Workers, Vercel), where push and suspension fit naturally
  • The application needs durable state per entity (carts, accounts, agent sessions) alongside workflows
  • Low latency matters and processes are many short steps
  • The team prefers code that reads like ordinary request handlers

Temporal tends to fit when…

  • The team wants the most established option, with a large community and long production history
  • They need an SDK in a language Restate doesn't cover, or deep testing tools
  • Workers inside a private network that only makes outbound connections suit their security model
  • They're already invested in it, or have hired people who know it
  • Very long-running processes with explicit, enforced separation between orchestration and side effects

Either works for…

Order processing, payments, onboarding flows, AI agent loops, sagas across services, scheduled jobs. The patterns in Modules 3 and 4 map almost one-to-one.

How to talk about a competitor

  • Describe, don't disparage. "Temporal pulls work through task queues; Restate pushes it to your services. Here's what that means for you."
  • Ground it in the customer's needs, not feature lists.
  • Admit trade-offs. Customers trust the person who says "for that requirement, the other product is a good fit."

These come up in every incident:

From: Marco Ruiz, Payments Engineer, Brightside Coffee · Priority: Urgent Subject: Restate charged a customer twice!!

A customer was charged twice for order bc-7731 yesterday. Our payment provider's dashboard shows two $49.99 charges eight seconds apart. We moved to Restate specifically to stop this. Is exactly-once broken?

The customer arrives with a theory ("exactly-once is broken") and real money at stake. Be careful: don't agree, don't argue. Get evidence.

Investigation

System of record first. The payment provider shows two charges. That's a fact.

Then Restate's view:

 [3]: Run command       charge card        +228ms
 [4]: Run notification  charge card        +1s      ← one step, completed once
 [5]: Run command       ship order
 >> completed with success

One invocation, one completed charge card step. Restate's record is internally consistent. So where did the second charge come from?

The service log has the answer:

TransientError: bank.charge: timed out waiting for response
Related command: run [charge card]

The step's first attempt timed out. Restate retried it, as it should for a transient error. The second attempt succeeded and was recorded.

Look at the code:

await ctx.run("charge card", () => bank.charge(order.orderId, order.amountCents));   // no idempotency key

Root cause

An ambiguous failure (lesson 1.3). The payment provider charged the card, but its response didn't arrive before the timeout. From inside the step, "charged but reply lost" looks exactly like "never charged", so the retry charged again. Without an idempotency key, the provider had no way to recognize the retry.

Restate's guarantee is that each step completes once and is never re-run after it's recorded. A step interrupted before it's recorded runs again: steps are at-least-once (lesson 2.4). Closing that gap takes the outside system's help.

Fix

Pass a stable idempotency key, the same on every attempt:

await ctx.run("charge card", () =>
  bank.charge(order.orderId, order.amountCents, { idempotencyKey: `${order.orderId}/charge` }),
);

Same fault, with the fix:

bank      charge               $49.99
bank      charge-deduplicated  duplicate ignored

Background: how Restate runs old orders on old code

When you register a service with Restate, that registration is a deployment: one version of your code, at one address (a URL, or a serverless function version). Restate pins every invocation to the deployment it started on. All its retries and replays go to that same code, even after newer versions are registered. New invocations go to the newest deployment.

So the normal way to ship a change is to run the new version at a new address and register it alongside the old one. Orders already in flight finish on the old code; new orders use the new code. Once nothing is running on the old deployment (it's drained), you remove it.

register --force breaks that model on purpose: it replaces an existing deployment in place, so in-flight invocations suddenly run the new code. That's convenient while developing on your own machine, and risky in production. Module 7 covers versioning in more depth.

Root cause

A non-deterministic code change (a step inserted in the middle) combined with a deploy method that moved in-flight invocations onto the new code. Either alone would have been harmless: with a proper deploy the old orders stay on v1, and with a --force deploy but no reordering the journals still line up.

Mitigation: roll back

Put v1's code back at the URL and re-register it. Stuck orders replay cleanly and finish. That's the fastest path to unstuck customers, before any fix.

Fix: deploy v2 beside v1

# v2 at a new URL, as a new deployment. v1 keeps running.
restate deployments register http://gift-v2.internal:9080
 ID       STATUS     PINNED_DEPLOYMENT_ID
 wr-502   suspended  dp_…v1     ← started before: stays on v1
 wr-503   completed  dp_…v2     ← started after: runs v2

Once v1 is drained (no active invocations: restate deployments describe <id> --extra), remove it with restate deployments remove <id> and shut it down. On serverless platforms and with Restate's Kubernetes operator, this versioning is automatic: each version gets its own endpoint, and old ones stay available until their invocations drain.

Durable workflows outlive deploys. An order started on Monday's code may still be waiting for pickup when Tuesday's code ships. Every durable execution platform needs an answer to "which code does an in-flight workflow run on?" Restate's answer is immutable deployments with pinning.

The model

flowchart LR
    subgraph Restate
        R[Router]
    end
    R -->|"invocations started<br/>before v2 registered"| V1["Deployment v1<br/>http://orders-v1/"]
    R -->|"new invocations"| V2["Deployment v2<br/>http://orders-v2/"]
    V1 -.->|"drained → remove"| X(( ))
  1. Each version is its own deployment at its own endpoint (URL, Lambda version, …).
  2. Invocations are pinned to the deployment they started on. Every retry and replay goes to that same code.
  3. New invocations go to the latest registered deployment for that service.
  4. When an old deployment has no active invocations, it's drained: remove it and shut it down.

Because of pinning, handlers don't need version checks like Temporal's patched(). The cost is operational: you must keep old versions running until they drain.

The workflow

# deploy the new code at a new endpoint, then:
restate deployments register http://orders-v2/
restate deployments list                           # v1 now marked "superseded"
restate deployments describe <v1-id> --extra       # active invocations still on v1?
restate deployments remove <v1-id>                 # once drained

On serverless platforms (Lambda versions, Cloudflare Workers, Vercel, Deno Deploy) and with Restate's Kubernetes operator, this happens automatically: each version gets its own endpoint, and old ones are kept until drained.

What breaks it

ActionResult
register --force on the same endpoint in productionIn-flight invocations move to the new code. Fine for bug fixes inside ctx.run; reordered/added/removed steps cause RT0016 journal mismatches (incident 6.3). The CLI warns that this is dangerous.
Removing a deployment before it's drainedIts in-flight invocations have nowhere to run
Very long-running handlersOld deployments take a long time to drain. Prefer splitting long processes into steps linked by delayed sends.
Renaming or removing a handlerRegistration rejects it unless you pass --breaking, because callers may still use the old name
Changing the shape of virtual object stateState outlives deployments: v2 must read what v1 wrote. Keep state schemas backward compatible.

Fixing a bug in invocations that are already running

Sometimes in-flight invocations need new code, for example a bug that makes them fail. If the fix doesn't change the sequence of Restate operations (a fix inside a ctx.run, say), move them to the fixed deployment:

restate deployments register http://orders-v2-fixed/
restate invocations pause <id>
restate invocations resume <id> --deployment <fixed-deployment-id>

If the fix does change the sequence, the old invocations must finish (or be cancelled and re-run) on code that matches their journals.

Support angle Versioning questions are among the most important you'll handle, because mistakes are painful and customers are often unsure what's safe. The key facts: invocations are pinned, --force is for local development, drain before removing, and state must stay compatible across versions. Incident 6.3 is the classic failure.

In Temporal, workers poll for work, so by default any worker on the task queue may pick up any workflow task, including tasks for executions that started on older code. The replayed code must still match each execution's history. Temporal gives you three tools.

1. Know what's safe to change

2. Patching

if (patched("gift-email")) {
  await acts.sendEmail(order.orderId, "We're preparing your gift");
}

The lifecycle of a patch:

  1. Add patched("id") around the new code and deploy. Old executions take the old path; new ones take the new path and record a marker.
  2. When no executions from before step 1 are still running, replace it with deprecatePatch("id") and keep only the new code.
  3. When no executions from before step 2 are running, remove the deprecatePatch call.

Patches accumulate if teams skip steps 2 and 3, which makes workflow code harder to read over time.

3. Worker Versioning

Temporal's newer approach is closer to Restate's pinning. Each worker deployment declares a version, and executions can be pinned to the version they started on, or allowed to auto-upgrade to the newest. Pinned executions finish on old workers, so changes don't need patching, but you run old and new workers side by side until old versions drain. Check the current Temporal docs for this feature's status and configuration in your SDK version.

Replay tests in CI

Whatever approach you choose, the best protection is to replay real histories against new code before deploying (lesson 4.10):

await Worker.runReplayHistory({ workflowsPath }, savedHistory);   // throws on non-determinism

A typical setup saves a sample of production histories (temporal workflow show --output json), commits them, and runs a replay test on every pull request.

Where the cost goes

Every durable step costs more than a plain function call, because its result has to be recorded durably before moving on. Throughput and latency depend on how many steps a process has and how fast the platform can record them.

LeverEffect
Fewer, coarser stepsFewer writes. But each step is a unit of retry: one giant ctx.run/activity re-runs entirely after a failure.
Parallel steps (Promise.all of calls/activities)Lower end-to-end latency
Large payloads in stepsBigger journals and histories, slower replays. Store big data elsewhere and journal a reference.
Long histories (Temporal)Slower replay, history limits: continue-as-new (4.8)

Restate

  • A Restate server is a single binary; for scale and availability it runs as a cluster. Work is split into partitions, each owning a range of invocations and keys, with a replicated log underneath for durability.
  • Your services scale like any HTTP service: more instances behind a load balancer, or serverless functions that scale automatically.
  • Virtual objects process one exclusive handler per key at a time, so throughput per key is limited by handler duration (incident 6.6). Throughput across keys scales out.

Temporal

  • The Temporal service is split into frontend, history, matching and internal worker services, backed by a database. Self-hosted clusters choose a fixed number of history shards when the cluster is created, and it can't easily be changed later, a well-known capacity-planning decision.
  • Workers scale horizontally: add more on the same task queue. Each worker has concurrency limits (how many workflow and activity tasks it runs at once) and a cache of recently used workflows.
  • Symptoms of too few workers: growing schedule-to-start latency (tasks waiting on the queue) with pollers present.

Serverless platforms (AWS Lambda, Cloudflare Workers, Vercel, Deno Deploy) run code per request and stop it afterwards, often with a time limit. That fits the push model naturally and the pull model less so.

Restate on serverless

Because Restate calls your code, a handler can be a serverless function:

  • Register a Lambda function version (its ARN) instead of a URL. Each published version is its own deployment, so versioning (7.1) comes for free.
  • Suspension (3.6) is what makes this work: while an invocation waits on a timer, a call or an awakeable, no function is running and nothing is billed. When it's time to continue, Restate invokes the function again and the SDK replays the journal.
  • A handler that waits 30 days is a few short function invocations, not a 30-day function.

Temporal and serverless

Temporal workers are long-running processes that poll, which doesn't fit "run per request" platforms directly. Workers usually run on VMs, containers or Kubernetes. Temporal announced a serverless option for its platform at its Replay 2026 conference. If a customer asks, check the current Temporal docs for what it supports.

Ticket 1: "Workflow stuck for 3 days"

We're on Temporal Cloud. Workflow invoice-88213 has been Running since Monday. The Web UI shows a pending activity generatePdf, attempt 2,914. Last failure: Error: ENOSPC: no space left on device.

Model answer

Bucket: nothing is happening / a step keeps failing. Diagnosis: the activity fails on every attempt because the worker host's disk is full. With Temporal's default retry policy (unlimited attempts), it will keep retrying. Nothing is lost: once disk space is freed, the next retry should succeed and the workflow continues. Reply: explain the cause, ask them to free disk on the workers (check for temp files generatePdf doesn't clean up), and note there's no need to restart the workflow. Suggest an alert on high activity attempt counts, and consider whether generatePdf leaks temp files, since that's likely the root cause.

Ticket 2: "Two welcome emails"

Restate. Since yesterday some new users get two welcome emails, a few seconds apart. Our signup handler: await ctx.run("save user", …); await sendWelcomeEmail(user);.

Model answer

Bucket: it happened twice. Diagnosis: sendWelcomeEmail is outside ctx.run, so it runs again on every replay. Any retry or suspension/resume of the invocation sends another email. It probably started yesterday because something made replays more common: a new ctx.sleep or call after the email, a slower dependency, a deploy. Reply: move the email into its own ctx.run (ideally with an idempotency key if the email provider supports one). Ask what changed yesterday to confirm.

Ticket 3: "Non-determinism after upgrading a library"

Temporal TypeScript. We upgraded our date library and bumped some dependencies. Now ~10% of running subscription workflows fail workflow tasks with a non-determinism error. New ones are fine.

Model answer

Bucket: broke after a deploy. Diagnosis: something in the dependency update changed the sequence of commands the workflow code produces for existing histories. Possibilities: the date library changed how it computes a duration passed to sleep (so a timer's duration or presence differs), or workflow code now branches differently. The 10% are workflows past the point where behavior differs. Reply: roll back first so they recover. Then save histories of affected workflows (temporal workflow show --output json) and replay them against the new code locally to pinpoint the change (Worker.runReplayHistory). Fix with patched() or Worker Versioning, and add those histories to a replay test in CI.

Model answer

Bucket: it failed and shouldn't have (or: misunderstanding). Diagnosis candidates: (a) the cart workflow continued as new or completed between signals, and the code doesn't carry or handle pending signals correctly (signals to a completed run are rejected, or state isn't carried over); (b) the handler isn't registered before awaiting, or has a bug; (c) they signal by run id, and the run changed. Signals that succeed are recorded in history, so the history settles it. Reply: ask for one affected workflow id and timestamp; look in the history for WorkflowExecutionSignaled events around that time. If the workflow continued as new, check that items are passed to the new run and that the workflow drains pending signals before continuing as new. Suggest signal-with-start to cover the case where the workflow has completed.

Ticket 6: "Payment provider says we're sending duplicate idempotency keys"

Restate. Our payment provider rejects some charges with "idempotency key already used with different parameters". We use the order id as the key.

Model answer

Bucket: it happened twice / design issue. Diagnosis: one key used for different operations or amounts: the charge and a later adjustment both use the order id, or a retry after the order changed sends a different amount. Idempotency keys must identify one operation with fixed parameters. Reply: use one key per operation (<orderId>/charge, <orderId>/adjust-1), and make sure the amount comes from the journaled order, not something recomputed that can change between attempts.

Ticket 7: "Should we migrate from our queue system?"

We run order processing on SQS + a status table + a cron sweeper. It mostly works but we get a few stuck orders a week. Would Restate help, and how hard is migration?

Model answer

Bucket: how do I…? (presales/onboarding). Reply: acknowledge what works today. Explain what durable execution replaces (status table, sweeper, hand-built retries) and what it doesn't (they still need idempotency keys for external calls). Suggest migrating one flow first, running both systems side by side, with new orders on Restate and old ones draining. Ask about volume, latency needs, where code runs and language. Offer a call. Be honest about effort: the logic ports easily; the work is deployment, observability and edge cases.

Ticket 8: "Timer fired 40 minutes late"

Temporal self-hosted. A 24h reminder fired 40 minutes late last night. Is the timer unreliable?

Model answer

Bucket: it's slow. Diagnosis: the timer fired on time (check TimerFired in the history), but the next workflow task waited because no worker picked it up: workers down, a deploy, or a backlog. Compare TimerFired with the next WorkflowTaskStarted timestamp. Reply: ask for the workflow id and check those timestamps. The shape

  1. Answer the scary question first. "No orders were lost." "Nothing was charged twice except bc-7731."
  2. Explain what happened in their terms, in a few sentences. Their order, their service, their deploy. Not the product's internals.
  3. Give the fix or workaround, concretely: a command, a code snippet, a link.
  4. Show how to verify it themselves.
  5. Flag the adjacent risk they didn't ask about ("do you send idempotency keys?").
  6. Offer the next step, if there is one.

Example article

Why was my customer charged twice?

Short answer: a payment call was retried after a timeout, and the payment provider wasn't given an idempotency key, so it couldn't tell the retry from a new charge. Add a stable key to fix it.

What happens: Restate records each step's result once it finishes, and never re-runs a recorded step. But if a call to another system is interrupted, for example by a timeout, Restate can't know whether that system already acted, so it retries the step. Your payment provider may then receive the same request twice.

How to fix it: pass an idempotency key that's the same on every attempt:

await ctx.run("charge card", () =>
  stripe.paymentIntents.create({ … }, { idempotencyKey: `${orderId}/charge` }));

Don't: generate the key randomly inside the step. It must be identical on every retry.

Check if you're affected: search your payment provider for pairs of identical charges within a few seconds of each other.
