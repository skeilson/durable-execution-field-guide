# 6.4 The stuck workflow nobody noticed

**Time:** 25 minutes · **Run:** `npm run m6 -- 6.4` · **Builds on:** 2.6, 3.5 · **Code:** [`services/stock-sync.ts`](../services/stock-sync.ts)

## The ticket

> **From:** Sam Okafor, Ops, Fernhill Grocers · **Priority:** Normal
> **Subject:** Stock levels haven't updated since yesterday
>
> Our nightly stock sync usually finishes in a minute. Since yesterday, store managers say stock levels are frozen. The Restate dashboard shows nothing failed. Restate is up. What's going on?

## Investigation

"Nothing failed" is true, and it's the clue. Look at what's **still in flight**:

```bash
npx restate invocations list
```

```
 [inv_11Sq…] StockSync/sync  backing-off (retry 4)
 [inv_10Kw…] StockSync/sync  backing-off (retry 4)
 … (all five)
```

```
Status:   backing-off  (Retried 4 time(s). Next retry in 3 seconds)
Error:    [500] supplier API: 401 Unauthorized (API key revoked)
Caused by: Run [fetch stock level from supplier]
```

> Use the CLI's list here, not a SQL filter on `status = 'backing-off'`: between attempts, SQL can briefly show `ready` instead (lesson 3.11).

## Root cause

The supplier API key was rotated without updating the service. Every call fails with 401. The handler throws an ordinary `Error`, so Restate treats it as transient and retries with the **default retry policy**: increasing delays, up to 70 attempts over roughly an hour, then **paused**. Nothing fails, so a failures-only dashboard stays green.

## Resolution

1. Fix the cause: deploy the new API key.
2. Retry everything now instead of waiting for backoff (or resuming paused ones):

```bash
npx restate invocations resume StockSync/sync
```

All five complete; no work lost.

## Prevention

| Measure | How |
| --- | --- |
| Alert on long-retrying or paused invocations | Scrape Restate's Prometheus metrics (`:5122/metrics`), or a scheduled job that checks `restate invocations list` for backing-off/paused entries older than N minutes |
| Classify errors deliberately | 401 isn't fixed by retrying in a minute, but it **is** fixable. Pausing is right here. A validation error should be a `TerminalError`. |
| Tune retry policy per handler | A nightly job can afford long backoff; a checkout can't |
| Alert on business outcomes | "No successful stock sync in 2 hours" catches what infrastructure alerts miss |

## Runbook entry

```
SYMPTOM   Work silently not happening; "nothing failed".
CHECK     restate invocations list           → backing-off / paused?
          restate invocations describe <id>  → last error
LIKELY    Persistent error (auth, config, downstream outage) retried as transient
FIX       Fix the cause, then: restate invocations resume <Service/handler>
PREVENT   Alert on retrying/paused invocations; terminal vs transient review
```

## In Temporal

Temporal's default activity retry policy has **no attempt limit**, so the same bug means activities retrying forever (with backoff capped at 100s) and workflows Running indefinitely. `temporal workflow describe` shows the pending activity's attempt count and last failure. After deploying the fix, the next retry succeeds. Alerting on long-pending activities (SDK or server metrics, or the Web UI's pending activity view) is the equivalent prevention.
