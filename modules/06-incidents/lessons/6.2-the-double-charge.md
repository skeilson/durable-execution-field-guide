# 6.2 The double charge

**Time:** 30 minutes · **Run:** `npm run m6 -- 6.2` · **Builds on:** 1.3, 2.4, 2.5 · **Code:** [`services/legacy-checkout.ts`](../services/legacy-checkout.ts)

## The ticket

> **From:** Marco Ruiz, Payments Engineer, Brightside Coffee · **Priority:** Urgent
> **Subject:** Restate charged a customer twice!!
>
> A customer was charged twice for order bc-7731 yesterday. Our payment provider's dashboard shows two $49.99 charges eight seconds apart. We moved to Restate specifically to stop this. Is exactly-once broken?

The customer arrives with a theory ("exactly-once is broken") and real money at stake. Be careful: don't agree, don't argue. Get evidence.

## Investigation

**System of record first.** The payment provider shows two charges. That's a fact.

**Then Restate's view:**

```
 [3]: Run command       charge card        +228ms
 [4]: Run notification  charge card        +1s      ← one step, completed once
 [5]: Run command       ship order
 >> completed with success
```

One invocation, one completed `charge card` step. Restate's record is internally consistent. So where did the second charge come from?

**The service log** has the answer:

```
TransientError: bank.charge: timed out waiting for response
Related command: run [charge card]
```

The step's first attempt **timed out**. Restate retried it, as it should for a transient error. The second attempt succeeded and was recorded.

**Look at the code:**

```ts
await ctx.run("charge card", () => bank.charge(order.orderId, order.amountCents));   // no idempotency key
```

## Root cause

An **ambiguous failure** (lesson 1.3). The payment provider charged the card, but its response didn't arrive before the timeout. From inside the step, "charged but reply lost" looks exactly like "never charged", so the retry charged again. Without an idempotency key, the provider had no way to recognize the retry.

Restate's guarantee is that each step **completes** once and is never re-run after it's recorded. A step interrupted before it's recorded runs again: steps are **at-least-once** (lesson 2.4). Closing that gap takes the outside system's help.

## Fix

Pass a **stable** idempotency key, the same on every attempt:

```ts
await ctx.run("charge card", () =>
  bank.charge(order.orderId, order.amountCents, { idempotencyKey: `${order.orderId}/charge` }),
);
```

Same fault, with the fix:

```
bank      charge               $49.99
bank      charge-deduplicated  duplicate ignored
```

**Common mistakes when adding keys:**

| Mistake | Why it fails |
| --- | --- |
| `idempotencyKey: crypto.randomUUID()` inside the step | New key on every attempt: the provider sees a new charge each time |
| Key generated *outside* `ctx.run` with `Math.random()` | Can change on replay. Use `ctx.rand.uuidv4()` (deterministic) or a business id. |
| Key = order id, reused for refunds too | Use a different key per operation (`/charge`, `/refund`) |

## In Temporal

Identical root cause and fix. An activity that times out (`startToCloseTimeout`) or whose worker dies after the provider charged is retried, and charges again without a key. A popular stable key in Temporal is the workflow id plus the activity id, both available inside the activity. One extra Temporal-specific trap: if `startToCloseTimeout` is shorter than the provider's normal response time, *every* slow charge times out and is retried, while the first attempt may still complete in the background.

## Reply to the customer

> Hi Marco,
>
> Thanks for the order id. I've traced bc-7731 end to end. Here's what happened and how to stop it.
>
> **What happened:** Restate ran checkout once, and its "charge card" step completed once. The step's *first attempt* timed out waiting for your payment provider, which (as your dashboard shows) had already charged the card. Restate treats a timeout as temporary and retries the step. Your provider couldn't tell the retry apart from a new charge, so it charged again.
>
> **Why this isn't an exactly-once bug:** Restate guarantees each step completes once and is never re-executed after it's recorded. But a step that's interrupted *while* calling another system has to be retried, because no system can know whether the other side acted before the timeout. The other system has to recognize the repeat, and that's what idempotency keys are for.
>
> **The fix** is one line. Your provider supports idempotency keys; pass a stable one per order and operation:
>
> ```ts
> await ctx.run("charge card", () =>
>   provider.charge(order, { idempotencyKey: `${order.orderId}/charge` }));
> ```
>
> Please don't generate the key randomly inside the step: it has to be the same on every retry.
>
> I'd also suggest searching your provider for other duplicate pairs since you went live, so you can refund any others. Happy to help write that query.
>
> Best,
> [Your name]
