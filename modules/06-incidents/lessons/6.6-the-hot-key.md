# 6.6 The hot key

**Time:** 25 minutes · **Run:** `npm run m6 -- 6.6` · **Builds on:** 3.7 · **Code:** [`services/loyalty-cart.ts`](../services/loyalty-cart.ts)

## The ticket

> **From:** Ana Lima, Engineering Manager, Tidepool Books · **Priority:** Normal
> **Subject:** Cart is slow for some customers, fine for others
>
> Adding to cart normally takes ~50ms. For some customers it sometimes takes 10+ seconds. It started after we launched loyalty rewards. It's always specific customers, never everyone at once.

"Specific customers, never everyone" in a system with virtual objects is a strong hint. Each customer is a key.

## Investigation

While one of ana's adds is slow:

```bash
npx restate invocations list --service LoyaltyCart --key ana
```

```
 LoyaltyCart/ana/add                 pending
 LoyaltyCart/ana/recalculateRewards  running
```

The `add` isn't running: it's **pending**, queued behind `recalculateRewards`, which is calling the partner rewards API (10+ seconds). Meanwhile ben's add, on a different key, took 0.02s.

## Root cause

```ts
recalculateRewards: async (ctx: restate.ObjectContext) => {          // exclusive (the default)
  const points = await ctx.run("ask partner for rewards", () => partnerRewardsApi(ctx.key));
  ctx.set("points", points);
}
```

Virtual objects run **one exclusive handler at a time per key**. That's what prevents race conditions (lesson 3.7), but it means a slow exclusive handler blocks every other request for that key until it finishes. Customers whose rewards were being recalculated when they shopped got stuck in line.

## Fix

Do the slow work **outside the queue**, and hold the queue only for the quick write:

```ts
refreshRewards: restate.handlers.object.shared(async (ctx) => {       // shared: doesn't queue
  const points = await ctx.run("ask partner for rewards", () => partnerRewardsApi(ctx.key));
  ctx.objectSendClient(loyaltyCart, ctx.key).storePoints(points);     // quick exclusive write
}),
```

ana's add during a rewards refresh: **0.01s**.

Other options, depending on the case: move the slow work to a separate service and send it the request; or keep the exclusive handler but make the external call faster (caching) or bounded (timeouts).

## Runbook entry

```
SYMPTOM   Latency for some keys (customers/accounts/devices), not all.
CHECK     restate invocations list --service <Object> --key <key>
          → pending invocations behind a long-running one?
LIKELY    Slow or waiting exclusive handler on that key (external call, sleep, awakeable)
FIX       Move slow work to a shared handler or another service; keep exclusive
          handlers short; never sleep/wait long in an exclusive handler
```

## In Temporal

The equivalent shows up with entity workflows (lesson 4.7): a workflow processes its signals and updates one at a time on a single thread of execution, so a long activity awaited inside an update handler holds up everything else. Fixes are similar: don't block message handlers on slow work, and run slow work concurrently or in a child workflow.
