# 6.3 The deploy that broke running orders

**Time:** 40 minutes · **Run:** `npm run m6 -- 6.3` · **Builds on:** 2.7, 3.2, 4.10 · **Code:** [`services/gift-v1.ts`](../services/gift-v1.ts), [`services/gift-v2.ts`](../services/gift-v2.ts)

## The ticket

> **From:** Priya Shah, Backend Lead, Wrapt Gifts · **Priority:** High
> **Subject:** Orders stuck after deploy with "mismatch between the code paths"
>
> We deployed a small feature (a gift-wrapping email) at 14:05. Orders placed after the deploy are fine. But some orders placed BEFORE it are now stuck retrying with error RT0016 "Found a mismatch between the code paths taken during the previous execution and the paths taken during this execution". Not all of them — maybe 1 in 20. What did we break?

## Investigation

`describe` on a stuck order:

```
Status:   backing-off
Error:    [570] Found a mismatch between the code paths taken during the previous
          execution and the paths taken during this execution.
          - The mismatch happened while executing 'run' (index '2')
          - Difference:
             name: charge card != send gift email
Journal:
 [1] Run reserve inventory   ✔
 [3] Run charge card         ✔
 [5] Sleep wait for pickup   ✔ fired
```

The error says exactly what changed: the journal's second step was `charge card`, and the new code asks for `send gift email` in that position.

**Why "some, not all"?** Orders that hadn't reached `reserve inventory` before the switch don't conflict: they run entirely on v2. Orders that were past it, sleeping until pickup, replay on v2 and hit the mismatch. The proportion depends on how many orders were mid-flight at the time.

**But why did old orders run v2's code at all?** Restate normally **pins** each invocation to the deployment it started on. Ask how they deployed:

> "We stopped the old container, started the new image at the same URL, and ran `restate deployments register --force`."

`--force` overwrites the existing deployment **in place**. The CLI even warns:

```
[WARNING]: This deployment is already known to the server … In-flight invocations to
this deployment might move to an unrecoverable failure state afterwards!
This is a DANGEROUS operation!
In production, we recommend creating a new deployment with a unique endpoint while
keeping the old one active until the old deployment is drained.
```

### Background: how Restate runs old orders on old code

When you register a service with Restate, that registration is a **deployment**: one version of your code, at one address (a URL, or a serverless function version). Restate **pins** every invocation to the deployment it started on. All its retries and replays go to that same code, even after newer versions are registered. New invocations go to the newest deployment.

So the normal way to ship a change is to run the new version at a **new** address and register it *alongside* the old one. Orders already in flight finish on the old code; new orders use the new code. Once nothing is running on the old deployment (it's **drained**), you remove it.

`register --force` breaks that model on purpose: it **replaces** an existing deployment in place, so in-flight invocations suddenly run the new code. That's convenient while developing on your own machine, and risky in production. Module 7 covers versioning in more depth.

## Root cause

A non-deterministic code change (a step inserted in the middle) **combined with** a deploy method that moved in-flight invocations onto the new code. Either alone would have been harmless: with a proper deploy the old orders stay on v1, and with a `--force` deploy but no reordering the journals still line up.

## Mitigation: roll back

Put v1's code back at the URL and re-register it. Stuck orders replay cleanly and finish. That's the fastest path to unstuck customers, before any fix.

## Fix: deploy v2 *beside* v1

```bash
# v2 at a new URL, as a new deployment. v1 keeps running.
restate deployments register http://gift-v2.internal:9080
```

```
 ID       STATUS     PINNED_DEPLOYMENT_ID
 wr-502   suspended  dp_…v1     ← started before: stays on v1
 wr-503   completed  dp_…v2     ← started after: runs v2
```

Once v1 is **drained** (no active invocations: `restate deployments describe <id> --extra`), remove it with `restate deployments remove <id>` and shut it down. On serverless platforms and with Restate's Kubernetes operator, this versioning is automatic: each version gets its own endpoint, and old ones stay available until their invocations drain.

## Runbook entry

```
SYMPTOM   After a deploy, some (not all) older invocations fail with RT0016
          "mismatch between the code paths". New invocations fine.
CHECK     describe → the "Difference" line names the changed step
          How was it deployed? Same URL + --force? Old deployment removed early?
MITIGATE  Roll back: restore the old code at the old deployment, resume
FIX       Redeploy the change as a NEW deployment (new URL/version), keep the old one
          until drained. If the old code is gone, a compatible fix can be deployed and
          stuck invocations moved with `resume --deployment`.
PREVENT   Never --force in production; drain before removing a deployment; add steps
          at the END of a handler where possible
```

## In Temporal

The same mistake produces a **non-determinism error** and repeated `WorkflowTaskFailed` (lesson 4.10). The workflow is stuck rather than lost. Mitigation is the same (roll back). Temporal's fixes differ: guard the change with `patched()`, or use Worker Versioning so old executions stay on old workers. Temporal teams also catch this before deploying by running **replay tests** against saved histories.
