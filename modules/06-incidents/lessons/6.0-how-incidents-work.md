# 6.0 How these incidents work

**Time:** 10 minutes

Every incident in this module is a support ticket played out for real. You run one command, and it:

1. shows the **ticket** as the customer wrote it
2. **reproduces** the problem on a real Restate server
3. **investigates** with the same CLI output you'd see on a call with the customer
4. asks you to **predict the root cause** before revealing it
5. applies the **fix** and **verifies** it against the system of record

```bash
npm run m6 -- 6.2      # one incident
npm run m6             # all of them
```

Each write-up in this module then has what a support engineer produces afterwards: the diagnosis, the reply to the customer, an internal note for engineering, and a **runbook entry** so the next person solves it faster.

## Before you start: the support habits

These come up in every incident:

- **Get an identifier.** An order id, invocation id or workflow id turns a vague report into something you can look up.
- **Ask the platform, then the system of record.** Restate's view (status, journal) plus the outside truth (payment provider, warehouse) together tell the story.
- **Separate "what happened" from "what to do."** Customers often start with a theory ("exactly-once is broken"). Gather evidence before agreeing or disagreeing.
- **Mitigate, then fix, then prevent.** Get the customer unstuck first (roll back, resume), then fix the cause, then suggest what stops it happening again.
- **Write it down.** A runbook entry turns one solved ticket into many.
