# 6.5 The timeout that caused duplicates

**Time:** 25 minutes · **Run:** `npm run m6 -- 6.5` · **Builds on:** 1.3, 3.4

## The ticket

> **From:** Lena Novak, Mobile Lead, Kestrel Outdoor · **Priority:** High
> **Subject:** Customers getting two orders from one tap
>
> Since we added an 8-second warehouse check to checkout, some customers get two identical orders. Our mobile app calls our API gateway, which calls Restate. The gateway times out after 5 seconds, and the app retries on timeout. We never retried more than once.

## Investigation

```
 ID                STATUS     IDEMPOTENCY_KEY             CREATED_AT
 inv_10HY…         completed  01M5T9J6733T…               19:45:52
 inv_1lpw…         completed  01M5T9JB3D9X…               19:45:57   ← 5 seconds later
```

Two invocations, five seconds apart, each with an **auto-generated** idempotency key. Restate saw two separate requests.

The ledger:

```
inventory reserve              ← twice
bank      charge
bank      charge-deduplicated  ← the bank ignored the repeat
email     send                 ← twice
shipping  ship                 ← twice
```

The charge was protected, because the Payments service already sends the bank an idempotency key, but nothing else was.

## Root cause

A client-side timeout only means **the client stopped waiting**. The first request was still running on Restate, and finished. The retry arrived as a new request with no way to tie it to the first. Checkout got slower (8s) than the gateway's timeout (5s), so *every* checkout now triggered a retry.

## Fix

Send a **stable idempotency key** with every attempt, created once per checkout tap (for example in the app, before the first request):

```bash
curl localhost:8080/Orders/checkout -H 'idempotency-key: ks-89' --json '…'
```

On retry, Restate attaches the second request to the first invocation and returns its result. One order:

```
 ID          STATUS     IDEMPOTENCY_KEY
 inv_1l7d…   completed  ks-89
```

Better still for slow operations: submit with `/send` (returns an invocation id right away) and get the result later with `/restate/invocation/<id>/attach` or `/output`. Then gateway timeouts don't matter.

## Runbook entry

```
SYMPTOM   Duplicate orders/requests, seconds apart, after something got slower.
CHECK     SQL/list: two invocations? Different idempotency keys? Gap = client timeout?
LIKELY    Client timeout + retry without an idempotency key
FIX       Stable idempotency key per user action, sent on every attempt
          (and/or /send + attach for long operations)
PREVENT   Client timeouts > p99 latency; idempotency keys as standard for writes
```

## In Temporal

The equivalent fix is choosing the **workflow id** from the business action (`checkout-<orderId>`): Temporal refuses to start a second running execution with the same id, so the retry gets "already started" and can wait for the existing one's result instead. A random workflow id per request reproduces this incident exactly.
