# 3.6 Timers and suspension

**Time:** 20 minutes · **Code:** [`shop/reminders.ts`](../shop/reminders.ts)

## `ctx.sleep`

```ts
remind: async (ctx, req) => {
  await ctx.sleep({ seconds: req.inSeconds }, "wait until reminder is due");
  await ctx.run("send reminder", () => email.send(req.orderId, "Your cart misses you"));
}
```

Just like engine v6, the sleep is journaled with its **wake-up time**. Unlike engine v6, nothing has to keep running while it waits.

## Suspension

When a handler is waiting on something that will take a while (a timer, a call to another service, a promise from lesson 3.8), the Restate SDK can **suspend** the invocation:

1. The service tells Restate "I'm waiting on entry #1" and **ends the request**. The process is free.
2. Restate holds the timer.
3. When the timer fires, Restate calls the handler again with the journal. The SDK replays to the line after `sleep` and continues.

```
Status:   suspended
Journal:
 [1]: Sleep command  wait until reminder is due
   └ until 13:27:06 (in 10s)
Last Event:
  Suspended after entry #1
    waiting on: Sleep [wait until reminder is due] (entry #1) or cancel
```

This is what lets a Restate handler wait 30 days, or run on a serverless platform that kills functions after 15 minutes.

Restate doesn't suspend instantly. By default the SDK keeps the request open for about a minute (the **inactivity timeout**) in case the wait is short, which saves a round trip. The reminders service sets it to 1 second so you can watch suspension happen:

```ts
restate.service({ name: "Reminders", options: { inactivityTimeout: { seconds: 1 } }, … })
```

## Two crashes, two outcomes

| When the service dies | Status | What Restate does |
| --- | --- | --- |
| While the handler is **actively running** (lesson 3.3) | `backing-off`, with "connection refused" | Retries until the service is back |
| While the invocation is **suspended** (this lesson) | Still `suspended`, no errors | Nothing, until the timer fires. Then it needs the service, and retries if it's still down |

## Delayed messages

Lesson 3.4 used a **delayed send**: "deliver this message in 3 seconds." That's the other way to schedule work later, without a handler waiting at all:

| | Use it when |
| --- | --- |
| `ctx.sleep(…)` then continue | The waiting is *part of* a process ("wait for pickup, then ship") |
| Delayed send | You want to *schedule a separate action* ("ask for a review in 7 days") |

Clients can schedule from outside too, with `?delay=` on the ingress URL: `curl 'localhost:8080/Emails/send/send?delay=7d' --json '…'` is accepted with an `executionTime` a week from now.

> **🎧 Support angle**
> Timer tickets: "my timer fired late" (was a service available when it was due? check for backing-off around that time), "can I cancel a scheduled job?" (yes: `restate invocations cancel <id>`), "does a deploy reset my timers?" (no: they live in Restate). And customers sometimes worry that a `suspended` invocation is stuck. Suspended is healthy: it's waiting, and `describe` says what it's waiting on.
