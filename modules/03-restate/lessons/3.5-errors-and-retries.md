# 3.5 Errors, retries and `TerminalError`

**Time:** 30 minutes · **Code:** [`shop/payments.ts`](../shop/payments.ts), [`shop/inventory-sync.ts`](../shop/inventory-sync.ts)

## The rule

Restate sorts every error into one of two kinds, using one simple rule:

| Thrown | Restate does |
| --- | --- |
| `TerminalError` | **Stops.** The invocation fails, and the error goes back to the caller. Never retried. |
| **Anything else** | **Retries** with growing delays, according to the retry policy |

Retrying is the default because it's the safe choice for a system that must not lose work. If the developer doesn't say an error is final, Restate assumes it might go away.

## A) Transient failure: retried automatically

The bank returns `503` four times, then recovers. Checkout's code has no retry logic, yet the order completes with one charge. While it's failing, the lesson shows the payment invocation:

```
Status:   backing-off
Error:    [500] bank.charge: 503 Service Unavailable
Caused by: Run [call the bank]
```

Retries happen **per invocation**: `Payments/charge` retries; `Orders/checkout` simply waits for its answer.

## B) Permanent failure: `TerminalError`

```ts
try {
  return await bank.charge(…);
} catch (err) {
  if (err instanceof PermanentError) throw new restate.TerminalError(`Card declined for ${orderId}`);
  throw err;   // anything else: let Restate retry
}
```

The developer translates "declined" into a `TerminalError`. It fails `Payments/charge`, and because Orders called Payments with `serviceClient`, the error **propagates** to Orders, then to the client. The customer gets an answer immediately instead of a request that hangs while Restate retries something hopeless.

The stock reserved before the charge stays reserved. Lesson 3.10 shows how to undo it.

## C) A retry policy that pauses

By default, Restate retries many times with growing delays, then **pauses** the invocation (lesson 2.6). You can tune this per service or per handler:

```ts
sync: restate.handlers.handler(
  {
    retryPolicy: {
      maxAttempts: 4,
      initialInterval: { milliseconds: 300 },
      exponentiationFactor: 2,
      onMaxAttempts: "pause",   // or "kill"
    },
  },
  async (ctx, sku) => { … },
),
```

After four failed attempts, the invocation is **paused**:

```
Status:   paused
Last Event:
  Paused after entry #1
    error: supplier API: 500 Internal Server Error
    failed at: Run [ask supplier for stock level] (command #1)
    stacktrace: …inventory-sync.ts:32…
[TIP]: Run `restate invocations resume inv_…` to resume the paused invocation
       once its cause is fixed.
```

A paused invocation keeps its journal and waits for a person. Fix the cause (deploy a fix, rotate a key, wait out the supplier's outage), then:

```bash
npx restate invocations resume <id>
npx restate invocations resume InventorySync/sync     # or: every invocation of that handler
```

If the fix is new code, `--deployment latest` resumes the invocation on the newest deployment, as long as the new code takes the same steps up to where the invocation stopped (Module 7).

| `onMaxAttempts` | What happens | When to choose it |
| --- | --- | --- |
| `pause` (default) | Stops retrying, keeps everything, waits for a human | Almost always: nothing is lost |
| `kill` | Fails the invocation for good | When a stale result is worse than no result |

## Choosing what's terminal

This is a design decision customers ask about constantly. A useful test: **would trying again in an hour give a different answer?**

| Error | Terminal? | Why |
| --- | --- | --- |
| 503, timeout, connection refused | No | Likely to recover |
| 429 Too Many Requests | No | Will recover after a wait |
| Card declined, insufficient funds | Yes | Same card, same answer |
| Validation error (bad input) | Yes | Same input, same answer |
| 401 Unauthorized (bad API key) | Usually no | It *is* fixable: rotate the key, then resume. Pausing beats failing every order. |
| A bug in your code (`TypeError`) | No | Deploy a fix; the retry picks it up |

That last row is one of the best features of durable execution: a bug doesn't lose work. Invocations retry or pause until a fix is deployed, then continue.

> **🎧 Support angle**
> "Restate keeps retrying my failed request!" usually means an error that should be terminal isn't marked as one. "My invocation is paused" means retries ran out. In both cases `describe` shows the last error and the exact step, often with a stack trace. Read it before guessing.
