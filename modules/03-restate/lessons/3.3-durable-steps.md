# 3.3 Durable steps with `ctx.run`

**Time:** 30 minutes · **Code:** [`shop/orders.ts`](../shop/orders.ts)

## The checkout

```ts
checkout: async (ctx: restate.Context, order: Order) => {
  const reservation = await ctx.run("reserve inventory", () =>
    inventory.reserve(order.orderId, order.sku));

  const payment = await ctx.serviceClient(payments).charge({ … });   // lesson 3.4

  ctx.serviceSendClient(emails).send({ … });                         // lesson 3.4

  await ctx.sleep({ seconds: PICKUP_WAIT }, "wait for warehouse pickup");

  const tracking = await ctx.run("ship order", () =>
    shipping.ship(order.orderId, order.address));

  return { orderId: order.orderId, reservation, payment, tracking };
}
```

`ctx.run(name, fn)` is Restate's version of your `ctx.step`: run `fn` once, record its result in the journal, and on replay return the recorded result without running `fn` again. The name is for humans: it shows up in the CLI and UI.

## The rules of `ctx.run`

These come straight from Module 2:

1. **Every side effect goes in a `ctx.run`.** Calls to databases, APIs and payment providers, plus anything else that touches the outside world. A side effect outside `ctx.run` repeats on every replay.
2. **The result must be serializable** (convertible to JSON), because it's stored in the journal. Return the data you need, not a database connection or a class instance.
3. **It's at-least-once.** If the service dies while `fn` is running, `fn` runs again. Pass idempotency keys to outside systems (lesson 2.5).
4. **Don't use `ctx` inside `ctx.run`.** A `ctx.run` is one side effect, not a mini workflow.

## Crash it

The lesson sends an order with `/send` at the end of the URL. That means "accept it and give me the invocation id; don't wait for the result". Then it kills the shop while the order waits for pickup.

> **▶ Run it**
> ```bash
> npm run m3 -- 3.3
> ```

You'll see `restate invocations describe` output like this, which is the single most useful command in Restate support:

```
Status:   backing-off  (Retried 4 time(s). Next retry in 168 ms.)
Error:    [500] error when calling 'http://localhost:9080/':
          h2 pool connection error: Connection refused (os error 111)

Journal:

 [2]: Run notification    reserve inventory   └ completion of [1]
 [3]: Call command                            └ → Payments/charge

 [8]: Sleep command       wait for warehouse pickup
 [9]: Sleep notification  wait for warehouse pickup
 >> backing-off
```

## Reading a Restate journal

The journal has more entries than you have lines of code, because Restate records both what your code **asked for** and what **came back**:

| Entry type | Means |
| --- | --- |
| `Input command` | The request that started the invocation |
| `Run command` / `Run notification` | "I'm running this side effect" / "here's its result" |
| `Call command` / `Call notification` | "I called another handler" / "here's its answer" |
| `OneWayCall command` | "I sent a message without waiting" |
| `Sleep command` / `Sleep notification` | "Wake me at time T" / "the timer fired" |
| `Output command` | The handler's final result |

A **command** with no matching **notification** yet is something in flight. That's often exactly where to look when an invocation is stuck.

## Recovery

Once the shop is back, `restate invocations resume` tells Restate to retry now instead of waiting out the current backoff. The order finishes, and the ledger shows one charge and one shipment.

> **🎧 Support angle**
> A crashed service is the most reassuring ticket you'll handle: the answer is almost always "nothing was lost; it will resume once the service is healthy." Incident 6.1 turns this lesson into a full incident write-up. The skill to practice now is reading `describe`: **status, last error, last journal entry.**
