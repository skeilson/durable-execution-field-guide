# 3.4 Calling, sending and idempotency

**Time:** 25 minutes · **Code:** [`shop/orders.ts`](../shop/orders.ts), [`shop/payments.ts`](../shop/payments.ts), [`shop/emails.ts`](../shop/emails.ts)

## Services calling services

Real systems are split into several services. In Restate, one handler calls another **through `ctx`**, so the call itself is journaled. Checkout uses all three styles:

```ts
// 1. Call and wait for the answer
const payment = await ctx.serviceClient(payments).charge({ orderId, amountCents });

// 2. Send and don't wait (fire and forget)
ctx.serviceSendClient(emails).send({ orderId, subject: "Thanks for your order" });

// 3. Send, but deliver later
ctx.serviceSendClient(emails).send(
  { orderId, subject: "How was your order?" },
  restate.rpc.sendOpts({ delay: { seconds: 3 } }),
);
```

| Style | Use it when | What's guaranteed |
| --- | --- | --- |
| **Call** (`serviceClient`) | You need the answer to continue | The call happens once; its answer is journaled, so a replay doesn't call again |
| **Send** (`serviceSendClient`) | The caller shouldn't wait (emails, notifications, kicking off background work) | Once Restate accepts the send, the target **will** run, even if the caller crashes right after |
| **Delayed send** | Something should happen later (a review request, a reminder) | Restate holds the message durably and delivers it at the time; no cron job needed |

Each call or send becomes its own invocation with its own id and journal, linked to the caller. The lesson queries this:

```sql
SELECT target, status, invoked_by_target FROM sys_invocation
```

```
 TARGET           STATUS     INVOKED_BY_TARGET
 Orders/checkout  completed
 Payments/charge  completed  Orders/checkout
 Emails/send      completed  Orders/checkout
 Emails/send      completed  Orders/checkout
```

> **Compare with Module 1:** a plain program that sends an email and then crashes has no idea whether the email went out. Here, the send is in the journal. On replay it isn't sent again, and Restate guarantees delivery.

## Idempotency at the front door

Lesson 2.5 covered idempotency keys for calls *out* to other systems. Restate also accepts them on calls coming *in*. Send the header `idempotency-key` with any request:

```bash
curl localhost:8080/Orders/checkout \
  -H 'idempotency-key: order-34' \
  --json '{"orderId":"order-34", …}'
```

If the same key arrives again (a double-clicked button, a client retrying after a timeout), Restate **doesn't start a second invocation**:

- If the first is still running, the second request attaches to it and gets the same result when it finishes.
- If the first already finished, Restate returns its stored result.
- With `/send`, the response says `"status": "PreviouslyAccepted"` instead of `"Accepted"`.

Restate remembers keys for a retention period (1 day by default, configurable per service or handler).

## Two kinds of idempotency, together

| | Protects against | Where |
| --- | --- | --- |
| **Ingress idempotency key** (header) | The *client* sending the same request twice | Restate, at the front door |
| **Idempotency key to outside systems** (in `ctx.run`) | A step re-running after a mid-step crash | The outside system (the bank) |

Look at [`shop/payments.ts`](../shop/payments.ts): the bank call passes `${orderId}/charge`, which stays the same on every retry. The shop uses both kinds.

> **🎧 Support angle**
> "We got two orders from one click" usually means the client app retried without an idempotency key, so Restate saw two different requests. Ask whether they send `idempotency-key`, and whether the key is stable (an order id or a client-generated id saved before the first attempt, not something generated fresh on each retry).
