# 4.8 Child workflows and continue-as-new

**Time:** 25 minutes · **Code:** [`shop/workflows.ts`](../shop/workflows.ts) (`batchCheckout`, `cart`)

## Child workflows

A workflow can start other workflows and wait for them:

```ts
export async function batchCheckout(orders: Order[]) {
  const results = await Promise.allSettled(
    orders.map((o) => executeChild(checkout, { workflowId: `batch-${o.orderId}`, args: [o] })),
  );
  …
}
```

Each child is a full workflow execution with its own id, history, retries and status. You can find and inspect each one on its own:

```bash
temporal workflow list --query "WorkflowType = 'checkout'"
```

Use children to break big processes into parts, to give each item in a batch its own history, or to run a part on a different task queue. A **parent close policy** decides what happens to children if the parent ends first: terminate them (the default), cancel them, or let them keep running.

Restate's equivalent is simply one handler calling another (lesson 3.4): every call is its own invocation already.

## History limits and continue-as-new

Every event in a workflow's history is stored and replayed. Histories can't grow forever: Temporal warns as a history gets large, and **terminates** a workflow whose history passes a hard limit (by default around 50,000 events or 50 MB). A long-lived entity workflow like a cart, receiving signals for months, will eventually hit it.

The fix is **continue-as-new**: the workflow ends its current run and immediately starts a new run, with the same workflow id, a fresh empty history, and whatever state you pass along:

```ts
await condition(() => orderId !== undefined || events >= 100);
if (orderId === undefined) {
  await continueAsNew<typeof cart>(customer, items);   // new run, same id, carry the items
}
```

In the lesson, 105 signals push the cart past 100 events, and the list shows two runs:

```
Status          WorkflowId  Type  …
ContinuedAsNew  cart-lee    cart
Running         cart-lee    cart
```

The shop uses 100 events so you can see it happen. Real workflows use thousands, or check `workflowInfo().continueAsNewSuggested`, which the server sets when the history is getting large.

> **▶ Run it**
> ```bash
> npm run m4 -- 4.8
> ```

Restate's journals have no comparable per-invocation limit in normal use, and its virtual objects keep state outside any one invocation's journal, so long-lived entities don't need this pattern. It's a real design difference.

> **🎧 Support angle**
> "My workflow was terminated and I didn't do it" is often a history limit: look for the termination reason in the history. Before that, Temporal emits warnings as the history grows. Workflows that loop forever (polling, subscriptions, entities) need continue-as-new from day one. A related ticket: replay getting slow on workflows with very long histories, which has the same fix.
