# 4.6 Timers

**Time:** 15 minutes · **Code:** [`shop/workflows.ts`](../shop/workflows.ts) (`reminder`)

```ts
export async function reminder(orderId: string, inSeconds: number) {
  await sleep(`${inSeconds} seconds`);
  await acts.sendEmail(orderId, "Your cart misses you");
}
```

`sleep` from `@temporalio/workflow` is a durable timer: it adds `TimerStarted` to the history, and the **server** holds the timer. When it fires, Temporal adds `TimerFired` and schedules a workflow task to continue.

Durations can be numbers (milliseconds) or strings like `"30 seconds"`, `"2 hours"` or `"7 days"`.

## No worker needed while waiting

A sleeping workflow doesn't occupy a worker. In the lesson, the worker is killed during a 12-second timer. Nothing errors. When the timer fires, the next workflow task waits on the queue until a worker returns, then the reminder goes out.

Temporal workers do keep recently active workflows cached in memory, so a short wait often resumes without a full replay. That's a performance detail; correctness never depends on it.

## Timers with a condition

Often you want "wait for X, but not forever." `condition` waits until a function returns true, with an optional timeout:

```ts
const decided = await condition(() => decision !== undefined, "7 days");
if (!decided) { /* timed out */ }
```

`returnRequest` (lesson 4.7) uses exactly this.

## Compared with Restate

| | Restate | Temporal |
| --- | --- | --- |
| Sleep | `ctx.sleep(…)` | `sleep(…)` |
| Wait for an event, with a timeout | Race a promise against `ctx.sleep` | `condition(fn, timeout)` |
| Schedule a separate action later | Delayed send | Start a workflow with a start delay, or a **Schedule** (Temporal's built-in cron) |
| Service/worker down when timer fires | Restate retries the call (backing-off, visible errors) | Task waits on the queue (no error) |

> **🎧 Support angle**
> "My timer fired late" in Temporal almost always means no worker was available when it fired: check worker uptime and task queue backlog at that time. "Can I change a sleeping workflow's timer?" isn't directly possible. The usual design is to wait on a `condition` that a signal can change, so the timer can be shortened or cancelled from outside.
