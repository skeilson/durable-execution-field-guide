# 4.10 The determinism sandbox, versioning and replay testing

**Time:** 40 minutes · **Code:** [`shop/workflows.ts`](../shop/workflows.ts), [`workflows-changed.ts`](../shop/workflows-changed.ts), [`workflows-patched.ts`](../shop/workflows-patched.ts)

Lesson 2.7 showed two ways to break replay: decisions that change between runs, and code that changes under a running workflow. Temporal handles the first with a **sandbox** and gives you **patching** and **replay testing** for the second.

## The sandbox

The TypeScript SDK bundles your workflow code and runs it in an isolated environment inside the worker:

| In workflow code | What happens |
| --- | --- |
| `Math.random()` | Replaced with a seeded generator, so replay produces the same numbers |
| `Date.now()`, `new Date()` | Return the time of the current workflow task, which is the same on replay |
| `setTimeout` | Becomes a durable timer |
| `fetch`, `fs`, network, files | Not available: use an activity |
| Importing activity *code* | Fails to bundle or run: import activity *types* only |

So the gift-wrap coin flip from lesson 2.7 is safe in a Temporal workflow without any extra helpers. The sandbox is stricter than Restate, which gives you deterministic helpers on `ctx` (`ctx.rand`, `ctx.date`) and trusts you to use them.

## Code changes: the history must still line up

The sandbox can't save you from changing the code. `workflows-changed.ts` adds an email between reserve and charge:

```ts
await acts.reserveInventory(…);
await acts.sendEmail(order.orderId, "We're preparing your gift");   // NEW
await acts.chargeCard(…);
```

A workflow that **started on the old code** has a history saying "after reserve, charge was scheduled." Replaying it on the new code, the worker schedules an email instead, and Temporal stops with a **non-determinism error**. The workflow task fails and is retried, and the workflow sits Running until a compatible version of the code is deployed.

## Patching

`patched` lets one version of the code serve both old and new executions:

```ts
await acts.reserveInventory(…);
if (patched("gift-email")) {
  await acts.sendEmail(order.orderId, "We're preparing your gift");
}
await acts.chargeCard(…);
```

| Execution | `patched("gift-email")` returns | Path |
| --- | --- | --- |
| Started before the change, replaying | `false` | Old: history still lines up |
| Started after the change | `true` (and records a marker in the history) | New |

Once every old execution has finished, replace `patched` with `deprecatePatch("gift-email")`, then later remove it entirely. Temporal also offers **Worker Versioning**, where each worker deployment declares a version and executions stay on the version they started with. That avoids patching for many changes, at the cost of running old and new workers side by side.

## Replay testing

You don't have to deploy to find out. The SDK can replay a saved history against new code, offline:

```ts
const history = await client.workflow.getHandle("gift-410a").fetchHistory();
await Worker.runReplayHistory({ workflowsPath: "…/workflows-changed.ts" }, history);
// → DeterminismViolationError
```

The lesson replays one real history against both versions:

```
✘ workflows-changed.ts: DeterminismViolationError: …
✔ workflows-patched.ts: replays cleanly
```

Teams save histories of real production workflows (`temporal workflow show --output json`) and replay them in CI before every deploy. It's the most effective protection against this whole class of incident.

> **▶ Run it**
> ```bash
> npm run m4 -- 4.10
> ```
> Part B does it live: a workflow starts on the old code, the careless version is "deployed" while it sleeps, the workflow gets stuck with `WorkflowTaskFailed`, and deploying the patched version un-sticks it.

## Compared with Restate

Restate takes a different approach to code changes: by default, an in-flight invocation **stays on the deployment version it started on** (Module 7). Old code keeps serving old invocations until they finish, and new invocations go to the new deployment. That's similar to Temporal's Worker Versioning, and it means Restate users rarely need patching, but they do need to keep old deployments available until their invocations drain.

> **🎧 Support angle**
> The non-determinism ticket: "after our deploy, some workflows are stuck with a non-determinism error; new ones are fine." First, **roll back** the deploy: stuck workflows recover on the old code. Then find the change (steps added, removed or reordered; a changed activity name), reintroduce it with `patched` or Worker Versioning, and recommend replay tests in CI.
