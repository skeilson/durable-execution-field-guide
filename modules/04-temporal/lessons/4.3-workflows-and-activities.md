# 4.3 Workflows and activities

**Time:** 30 minutes · **Code:** [`shop/workflows.ts`](../shop/workflows.ts), [`shop/activities.ts`](../shop/activities.ts), [`shop/worker.ts`](../shop/worker.ts)

## The checkout workflow

```ts
const acts = proxyActivities<typeof activities>({
  startToCloseTimeout: "10 seconds",
  retry: { initialInterval: "500 milliseconds", backoffCoefficient: 2, maximumInterval: "10 seconds" },
});

export async function checkout(order: Order) {
  const reservation = await acts.reserveInventory(order.orderId, order.sku);
  const payment = await acts.chargeCard(order.orderId, order.amountCents);
  await acts.sendEmail(order.orderId, "Thanks for your order");
  await sleep(`${order.pickupSeconds ?? 5} seconds`);
  const tracking = await acts.shipOrder(order.orderId, order.address);
  return { orderId: order.orderId, reservation, payment, tracking };
}
```

Compare it with Restate's [`orders.ts`](../../03-restate/shop/orders.ts). It's the same shape: top-to-bottom code, durable steps, a durable timer. The differences:

- Side effects are **activity calls** (`acts.chargeCard(…)`) instead of `ctx.run(…)` blocks.
- There's no `ctx`. Workflow functions use helpers imported from `@temporalio/workflow`.
- Every activity call must say how long one attempt may take (`startToCloseTimeout`). Temporal requires a timeout so it knows when to give up on an attempt and retry it.

## The worker

```ts
const worker = await Worker.create({
  connection,
  taskQueue: "shop",
  workflowsPath: "…/workflows.ts",   // bundled and run in a sandbox
  activities,                        // plain functions, run normally
});
await worker.run();
```

## Run it by hand

**Terminal 1:** `npm run temporal` · **Terminal 2:** `npm run worker` · **Terminal 3:**

```bash
temporal workflow execute --type greet --task-queue shop --workflow-id greet-1 --input '"Dana"'
temporal workflow execute --type checkout --task-queue shop --workflow-id order-43 \
  --input '{"orderId":"order-43","sku":"SKU-42","amountCents":4999,"address":"123 Main St","pickupSeconds":3}'
temporal workflow show --workflow-id order-43
```

`execute` waits for the result; `start` returns immediately. You choose the **workflow id**: Temporal allows only one *running* execution per id, which makes ids a natural idempotency key at the front door (like Restate's `idempotency-key` header).

## Reading an event history

`temporal workflow show` prints the history. A trimmed checkout:

```
  1  WorkflowExecutionStarted
  2  WorkflowTaskScheduled
  3  WorkflowTaskStarted
  4  WorkflowTaskCompleted
  5  ActivityTaskScheduled     reserveInventory
  6  ActivityTaskStarted
  7  ActivityTaskCompleted
  …
 17  TimerStarted
 18  TimerFired
  …
 27  WorkflowExecutionCompleted
```

| Events | Means |
| --- | --- |
| `WorkflowTask Scheduled / Started / Completed` | The worker ran your workflow code until it hit something to wait on, then reported "next, schedule this activity" |
| `ActivityTask Scheduled / Started / Completed` | One activity: queued, picked up by a worker, finished. Failed attempts show up as retries on the pending activity, not as separate events. |
| `TimerStarted / TimerFired` | A durable `sleep` |
| `WorkflowExecutionCompleted / Failed / Terminated / ContinuedAsNew` | How it ended |

Temporal's history is more fine-grained than Restate's journal: it records each round of decision-making (the workflow tasks), not just the steps.

> **🎧 Support angle**
> Customers new to Temporal often put API calls directly in workflow code. In TypeScript, the sandbox prevents most of this (no `fetch`, no `fs`), and the error message can be confusing. The fix is always the same: move the side effect into an activity.
