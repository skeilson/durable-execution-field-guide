# 4.7 Signals, queries and updates

**Time:** 35 minutes · **Code:** [`shop/workflows.ts`](../shop/workflows.ts) (`cart`, `returnRequest`, `asyncPayment`)

A running workflow can receive messages from outside. Temporal has three kinds:

| | Direction | Recorded in history? | Caller waits for | Use it to |
| --- | --- | --- | --- | --- |
| **Signal** | In | Yes | Nothing (fire and forget) | Deliver an event: "item added", "approved", "payment received" |
| **Query** | Out | No | The answer | Read state: "what's in the cart?" "what's the status?" |
| **Update** | In and out | Yes | The handler's result | Change state and get an answer: "check out and give me the order id" |

## Defining and handling them

```ts
export const addItem = defineSignal<[CartItem]>("addItem");
export const viewCart = defineQuery<{ items: CartItem[]; totalCents: number }>("viewCart");
export const checkoutCart = defineUpdate<string, [string]>("checkoutCart");

export async function cart(customer: string, items: CartItem[] = []) {
  setHandler(addItem, (item) => { items.push(item); });
  setHandler(viewCart, () => ({ items, totalCents: … }));
  setHandler(checkoutCart, async (address) => {
      const id = …;
      await acts.reserveInventory(id, …);     // the update does real work
      orderId = id;
      checkedOut = true;                      // only now is checkout finished
      return id;
    },
    { validator: (address) => { if (items.length === 0) throw new Error("Cart is empty"); } });

  await condition(() => checkedOut);         // wait for checkout to FINISH
  await condition(allHandlersFinished);      // never end with a handler still running
  return orderId;
}
```

Handlers update ordinary variables in the workflow. Because signals and updates are recorded in the history, replaying the history replays the same handler calls in the same order, so the variables always come out the same. Queries only read and leave no trace.

An update's **validator** runs before the update is accepted. Rejecting there gives the caller an error and leaves no trace in the history.

## A trap: ending while a handler is still running

An earlier version of this course had a bug worth learning from. The checkout handler set `orderId` **before** reserving the stock, and the workflow waited on `orderId !== undefined`. So as soon as checkout *started*, the main function saw an order id, returned, and the workflow completed, while the update handler was still waiting for its activity. Temporal then failed the update, and the caller saw only `Workflow Update failed`.

Two rules prevent it:

- Mark work as done **after** it's done (`checkedOut = true` comes after the activity).
- Before a workflow returns or continues as new, wait for `allHandlersFinished`. The SDK also logs a warning when a workflow ends with handlers still running. Look for it in worker logs.

## Three patterns from the lesson

> **▶ Run it**
> ```bash
> npm run m4 -- 4.7
> ```

**A) The entity workflow: a cart.** Temporal has no virtual objects (Restate lesson 3.7). The usual equivalent is one long-running workflow per entity, here workflow id `cart-dana`, with signals to change it, queries to read it and updates to act on it. **Signal-with-start** sends a signal and starts the workflow if it isn't running yet, so the client doesn't need to know whether the cart exists.

Like a Restate virtual object, a workflow processes its messages one at a time, so two `addItem` signals can't race.

**B) Waiting for a human: a return.** `returnRequest` waits on `condition(() => decision !== undefined, "7 days")`. An agent sends the decision as a signal:

```bash
temporal workflow signal --workflow-id return-47 --name decide --input '{"approved":true,"by":"sam@support"}'
```

and anyone can query the status in the meantime. Compare Restate's workflow with a durable promise (3.8): same idea, different mechanics.

**C) A webhook.** The payment provider's callback arrives at your web server, which forwards it to the workflow as a signal (the workflow id was passed to the provider as metadata). Compare Restate's awakeables (3.9). Temporal also supports **asynchronous activity completion**, where an activity hands out a task token and an outside system completes the activity with it, which is closer to an awakeable.

## Compared with Restate

| Need | Restate | Temporal |
| --- | --- | --- |
| State per entity, updated by many calls | Virtual object (built in) | Entity workflow + signals/updates |
| Read state while running | Shared handler | Query |
| Deliver an event to a running process | Call a handler that resolves a durable promise | Signal |
| Call in and get a result | Call a handler | Update |
| Wait for an external callback | Awakeable | Signal, or async activity completion |

> **🎧 Support angle**
> "My update failed but the workflow completed successfully" usually means the workflow ended while the update handler was still running: check for the unfinished-handler warning in the worker logs. Other common questions: "my signal was lost" (it wasn't: signals are in the history. Check whether the handler was registered before the workflow started waiting, and the signal **name**), "query returns stale data" (queries see state as of the last completed workflow task), "can I query a completed workflow?" (yes, within the namespace's retention period, by replaying its history on a worker, so a worker must be running).
