# 0.1 How this course works

**Time:** 10 minutes

## Who this is for

This course assumes you know nothing about durable execution and very little about programming. By the end you should be able to:

- explain durable execution to a customer or a colleague, in plain language
- build and run small programs on **Restate** and **Temporal**, the two leading durable execution platforms
- diagnose the problems customers actually hit, using the same tools a support engineer would
- write a clear reply to a customer ticket about any of it

## The shape of the course

| Module | What you'll learn | Hands-on |
| --- | --- | --- |
| **0 · Orientation** | How the course works, setup, terminal and code-reading basics | Install the tools |
| **1 · The problem** | Why programs fail halfway, and why "just retry" makes it worse | Break a checkout four ways |
| **2 · Core ideas** | Journals, replay, idempotency, retries, determinism, timers | Build a durable engine in six versions |
| **3 · Restate** | How Restate works and every major feature | Build an order system on Restate |
| **4 · Temporal** | How Temporal works and every major feature | Rebuild the same system on Temporal |
| **5 · Side by side** | Where the two products differ and why it matters | Compare your two builds |
| **6 · Incidents** | The tickets customers file, reproduced on purpose | Diagnose and fix seven incidents |
| **7 · Production** | Versioning, observability, scaling, security, operations | Revisit the incidents with production practices in mind |
| **8 · Supporting customers** | Reading tickets, writing replies, runbooks and knowledge-base articles | Work through eight ticket simulations |

Modules build on each other, so take them in order. Modules 1 and 2 are the foundation, and everything after them assumes you've done both.

## How each lesson works

Most lessons follow the same loop:

1. **Read.** A short explanation with a diagram. No jargon without a definition.
2. **Predict.** Before running anything, you'll be asked what you think will happen. Commit to an answer, even a guess. Being wrong and then seeing why is how this sticks.
3. **Run.** One command runs a real program on your machine, often crashing it on purpose.
4. **Reflect.** A few questions at the end of each module check your understanding.

You'll see two kinds of boxes:

> **▶ Run it**
> A command to type in your terminal.

> **🎧 Support angle**
> How this idea shows up in real customer tickets.

## Two ways to read

- **The interactive course site** has the same lessons plus step-through animations and quizzes. It's the best way to learn.
- **The GitHub repository** has every lesson as a page you can read on GitHub, plus all the code. It's what you'll run commands from.

## Keep a learning log

Create a file called `MY-NOTES.md` in the project folder (or use a notebook) and after each module, write down:

- one thing that surprised you
- one thing you'd explain differently to a customer
- one question you still have

Several lessons ask you to write something in your log. Putting an idea in your own words is the quickest way to find out whether you really understand it.
