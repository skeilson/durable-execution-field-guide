# 8.4 Runbooks and knowledge-base articles

**Time:** 40 minutes

A ticket solved once is a cost. A ticket turned into documentation is an investment: the next customer finds the answer themselves, or the next support engineer solves it in five minutes. At a young company, the first support engineer usually writes most of this.

## Runbook entries (for the support team)

Every incident in Module 6 ended with one. The format:

```
SYMPTOM   What the customer reports, in their words
CHECK     The commands to run, and what to look for
LIKELY    The usual causes, most likely first
FIX       What resolves it (mitigate first, then fix)
VERIFY    How to confirm it worked
ESCALATE  When this is no longer a customer problem
```

Short, scannable, command-first. Written for someone in a hurry.

## Knowledge-base articles (for customers)

Customer-facing articles answer one question each, with a title in the customer's words:

| Title (good) | Title (avoid) |
| --- | --- |
| Why was my customer charged twice? | Idempotency semantics of ctx.run |
| My workflow is stuck: how do I find out why? | Invocation lifecycle states |
| How do I deploy a new version without breaking running orders? | Deployment pinning |

## Example article

> ### Why was my customer charged twice?
>
> **Short answer:** a payment call was retried after a timeout, and the payment provider wasn't given an idempotency key, so it couldn't tell the retry from a new charge. Add a stable key to fix it.
>
> **What happens:** Restate records each step's result once it finishes, and never re-runs a recorded step. But if a call to another system is interrupted, for example by a timeout, Restate can't know whether that system already acted, so it retries the step. Your payment provider may then receive the same request twice.
>
> **How to fix it:** pass an idempotency key that's the same on every attempt:
>
> ```ts
> await ctx.run("charge card", () =>
>   stripe.paymentIntents.create({ … }, { idempotencyKey: `${orderId}/charge` }));
> ```
>
> **Don't:** generate the key randomly inside the step. It must be identical on every retry.
>
> **Check if you're affected:** search your payment provider for pairs of identical charges within a few seconds of each other.
>
> *Related: Idempotent requests to Restate · Handling timeouts*
