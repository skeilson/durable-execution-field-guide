# 8.1 How to read a ticket

**Time:** 20 minutes

Every incident in Module 6 followed the same path. This lesson makes it a habit you can apply to tickets you've never seen.

## The five questions

| # | Ask | Why |
| --- | --- | --- |
| 1 | **What is the customer actually worried about?** | "Is exactly-once broken?" really means "did customers lose money, and will it happen again?" Answer that first. |
| 2 | **What identifier can I look up?** | An order id, invocation id, workflow id or timestamp turns a story into evidence |
| 3 | **What does the platform say happened?** | Status, last error, journal/history (`describe`) |
| 4 | **What does the system of record say?** | Payment provider, warehouse, email logs. The outside truth. |
| 5 | **What changed?** | Deploys, config, traffic, a dependency. Most incidents follow a change. |

## Classify before you diagnose

Most durable execution tickets fall into a handful of buckets. Recognizing the bucket tells you where to look:

| Bucket | Typical words in the ticket | First place to look |
| --- | --- | --- |
| **Nothing is happening** | stuck, frozen, not running, "nothing failed" | `invocations list` / pending tasks and pollers |
| **It happened twice** | duplicate, charged twice, two emails | One invocation or two? Idempotency keys? |
| **It broke after a deploy** | mismatch, non-determinism, "only some" | What changed; how it was deployed |
| **It's slow** | latency, timeouts, "for some customers" | Hot keys, worker capacity, step count |
| **It failed and shouldn't have** | failed, cancelled, terminated | Terminal errors, retry limits, timeouts, history limits |
| **Setup / onboarding** | not found, can't connect, quickstart | Registration, URLs, task queue/namespace names |
| **How do I…?** | best practice, should we, can I | Docs, patterns, honest trade-offs |

## Asking for information

Every follow-up question costs the customer a round trip. Ask for everything you need **once**:

> To dig in, could you send:
> 1. One affected order id (or invocation id) and roughly when it happened
> 2. The output of `restate invocations describe <id>` for it
> 3. Whether anything was deployed or changed around that time
> 4. Restate Cloud or self-hosted, and which server and SDK versions

## Severity

| Severity | Examples | Response |
| --- | --- | --- |
| **Urgent** | Money moving wrongly, production down, data at risk | Respond immediately; mitigate first, explain later |
| **High** | Production degraded, workflows stuck at scale | Same day; workaround fast |
| **Normal** | One workflow misbehaving, development blocked | Steady progress with clear updates |
| **Low** | Questions, feature requests | Thorough answer, link docs |

On a small support team, you often also decide when to pull in an engineer. A useful rule: escalate when the evidence points to the platform, not the customer's code (for example, a journal that contradicts the system of record with no retry to explain it), or when severity is urgent and you can't mitigate within minutes.
