# 8.2 Ticket simulations

**Time:** 90 minutes

Eight tickets, with the evidence a customer might send. For each one:

1. **Classify** it (lesson 8.1).
2. Write down your **diagnosis** and what else you'd need to know.
3. Draft the **first reply** (3–8 sentences).
4. Only then open the model answer and compare.

Your answers don't need to match. If you'd ask a different question first, or catch something the model answer missed, note why. That reasoning is the skill this module is building.

---

## Ticket 1: "Workflow stuck for 3 days"

> We're on Temporal Cloud. Workflow `invoice-88213` has been Running since Monday. The Web UI shows a pending activity `generatePdf`, attempt 2,914. Last failure: `Error: ENOSPC: no space left on device`.

<details><summary>Model answer</summary>

**Bucket:** nothing is happening / a step keeps failing.
**Diagnosis:** the activity fails on every attempt because the worker host's disk is full. With Temporal's default retry policy (unlimited attempts), it will keep retrying. Nothing is lost: once disk space is freed, the next retry should succeed and the workflow continues.
**Reply:** explain the cause, ask them to free disk on the workers (check for temp files `generatePdf` doesn't clean up), and note there's no need to restart the workflow. Suggest an alert on high activity attempt counts, and consider whether `generatePdf` leaks temp files, since that's likely the root cause.
</details>

## Ticket 2: "Two welcome emails"

> Restate. Since yesterday some new users get two welcome emails, a few seconds apart. Our signup handler: `await ctx.run("save user", …); await sendWelcomeEmail(user);`.

<details><summary>Model answer</summary>

**Bucket:** it happened twice.
**Diagnosis:** `sendWelcomeEmail` is **outside** `ctx.run`, so it runs again on every replay. Any retry or suspension/resume of the invocation sends another email. It probably started yesterday because something made replays more common: a new `ctx.sleep` or call after the email, a slower dependency, a deploy.
**Reply:** move the email into its own `ctx.run` (ideally with an idempotency key if the email provider supports one). Ask what changed yesterday to confirm.
</details>

## Ticket 3: "Non-determinism after upgrading a library"

> Temporal TypeScript. We upgraded our date library and bumped some dependencies. Now ~10% of running `subscription` workflows fail workflow tasks with a non-determinism error. New ones are fine.

<details><summary>Model answer</summary>

**Bucket:** broke after a deploy.
**Diagnosis:** something in the dependency update changed the sequence of commands the workflow code produces for existing histories. Possibilities: the date library changed how it computes a duration passed to `sleep` (so a timer's duration or presence differs), or workflow code now branches differently. The 10% are workflows past the point where behavior differs.
**Reply:** roll back first so they recover. Then save histories of affected workflows (`temporal workflow show --output json`) and replay them against the new code locally to pinpoint the change (`Worker.runReplayHistory`). Fix with `patched()` or Worker Versioning, and add those histories to a replay test in CI.
</details>

## Ticket 4: "Is Restate down? 404 on everything"

> Since our deploy 20 minutes ago, every request returns `404 service 'Billing' not found`. Restate Cloud. Rolled back the app, still 404.

<details><summary>Model answer</summary>

**Bucket:** setup / onboarding, but in production, so **urgent**.
**Diagnosis:** Restate can't find a deployment serving `Billing`. Likely the deploy pipeline removed or replaced the registered deployment (for example, removed the old deployment and failed to register the new one), or the service was renamed. Rolling back the app doesn't re-register anything.
**Reply (fast):** ask them to run `restate deployments list` and `restate services list` against their Cloud environment and register the currently running endpoint. Then review the pipeline step that registers deployments. Also check whether in-flight invocations were pinned to a removed deployment.
</details>

## Ticket 5: "Cart updates lost"

> Temporal. Our cart is a workflow per user. Under load, some `addItem` updates seem to disappear. We send them with `client.workflow.signal` from a Lambda. Logs show the signal call succeeded.

<details><summary>Model answer</summary>

**Bucket:** it failed and shouldn't have (or: misunderstanding).
**Diagnosis candidates:** (a) the cart workflow **continued as new** or completed between signals, and the code doesn't carry or handle pending signals correctly (signals to a completed run are rejected, or state isn't carried over); (b) the handler isn't registered before awaiting, or has a bug; (c) they signal by run id, and the run changed. Signals that succeed are recorded in history, so the history settles it.
**Reply:** ask for one affected workflow id and timestamp; look in the history for `WorkflowExecutionSignaled` events around that time. If the workflow continued as new, check that items are passed to the new run and that the workflow drains pending signals before continuing as new. Suggest signal-with-start to cover the case where the workflow has completed.
</details>

## Ticket 6: "Payment provider says we're sending duplicate idempotency keys"

> Restate. Our payment provider rejects some charges with "idempotency key already used with different parameters". We use the order id as the key.

<details><summary>Model answer</summary>

**Bucket:** it happened twice / design issue.
**Diagnosis:** one key used for **different operations or amounts**: the charge and a later adjustment both use the order id, or a retry after the order changed sends a different amount. Idempotency keys must identify one operation with fixed parameters.
**Reply:** use one key per operation (`<orderId>/charge`, `<orderId>/adjust-1`), and make sure the amount comes from the journaled order, not something recomputed that can change between attempts.
</details>

## Ticket 7: "Should we migrate from our queue system?"

> We run order processing on SQS + a status table + a cron sweeper. It mostly works but we get a few stuck orders a week. Would Restate help, and how hard is migration?

<details><summary>Model answer</summary>

**Bucket:** how do I…? (presales/onboarding).
**Reply:** acknowledge what works today. Explain what durable execution replaces (status table, sweeper, hand-built retries) and what it doesn't (they still need idempotency keys for external calls). Suggest migrating **one flow** first, running both systems side by side, with new orders on Restate and old ones draining. Ask about volume, latency needs, where code runs and language. Offer a call. Be honest about effort: the logic ports easily; the work is deployment, observability and edge cases.
</details>

## Ticket 8: "Timer fired 40 minutes late"

> Temporal self-hosted. A 24h reminder fired 40 minutes late last night. Is the timer unreliable?

<details><summary>Model answer</summary>

**Bucket:** it's slow.
**Diagnosis:** the timer fired on time (check `TimerFired` in the history), but the next workflow task waited because no worker picked it up: workers down, a deploy, or a backlog. Compare `TimerFired` with the next `WorkflowTaskStarted` timestamp.
**Reply:** ask for the workflow id and check those timestamps. If there's a gap, look at worker availability and task queue backlog at that time. Suggest alerting on schedule-to-start latency and running enough workers with headroom.
</details>
