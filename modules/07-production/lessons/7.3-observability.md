# 7.3 Observability: logs, metrics and traces

**Time:** 25 minutes

Incident 6.4 showed the danger: durable systems are so good at retrying quietly that problems can sit unnoticed for hours. Observability is how teams find out before their customers do.

## Three signals

| Signal | Answers | Restate | Temporal |
| --- | --- | --- | --- |
| **Logs** | What did this code say? | `ctx.console` in handlers (quiet during replay); server logs | SDK `log` in workflows (replay-aware) and activities; server logs |
| **Metrics** | How much, how fast, how many failing? | Prometheus metrics from the server (port 5122, `/metrics`) | SDK metrics (Prometheus or OpenTelemetry, set up in the worker runtime) plus server or Cloud metrics |
| **Traces** | What path did this request take across services? | OpenTelemetry tracing export from the server | OpenTelemetry interceptors in the SDK |
| **Platform introspection** | What is the state of this execution right now? | CLI, UI, SQL (lesson 3.11) | CLI, Web UI, visibility queries (lesson 4.11) |

## What to alert on

Generic CPU and memory alerts miss most durable execution problems. These catch them:

| Alert | Catches |
| --- | --- |
| Invocations/activities retrying longer than N minutes | Silent retries (6.4), downstream outages |
| Restate: paused invocations > 0 | Retries exhausted, needs a human |
| Temporal: workflow task failures | Workflow code bugs, non-determinism (4.5, 4.10) |
| Temporal: task queue backlog / schedule-to-start latency | Not enough workers, or none (4.4) |
| Restate: invocations pending on one key for long | Hot keys (6.6) |
| Business outcomes ("no successful sync in 2h", "checkouts per minute dropped") | Everything above, plus things nobody thought of |

## Searchable business ids

Support works faster when executions can be found by **business** identifiers:

- **Restate:** use meaningful idempotency keys, object keys and workflow keys (an order id, a customer id), so `sys_invocation` can be searched by them (incident 6.1 found the order by its idempotency key).
- **Temporal:** use meaningful workflow ids (`checkout-<orderId>`), and add **custom search attributes** (customer id, order total) to filter in `workflow list --query` and the UI.

> **🎧 Support angle**
> On many tickets the most valuable thing you can do is help the customer set up the one alert that would have caught it. "Here's the fix, and here's the alert that would have paged you two hours earlier" is the kind of reply that builds trust.
