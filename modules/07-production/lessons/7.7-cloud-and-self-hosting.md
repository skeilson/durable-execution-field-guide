# 7.7 Managed cloud and self-hosting

**Time:** 15 minutes

Both companies offer a managed service and an open-source server you can run yourself. Customers often move between the two, and many support questions depend on which one they use.

| | Restate | Temporal |
| --- | --- | --- |
| **Managed** | Restate Cloud | Temporal Cloud |
| **Self-hosted server** | One binary; runs alone or as a cluster with a replicated log and snapshots to object storage | Several services (frontend, history, matching, worker) plus a database (PostgreSQL, MySQL or Cassandra), optionally Elasticsearch for advanced visibility; Helm charts for Kubernetes |
| **Your code runs** | Wherever you like: Restate calls it (containers, Kubernetes, serverless) | In your workers, wherever you run them; they connect out to the service |
| **Operational burden when self-hosting** | Lower: a single binary to run, upgrade and back up | Higher: multiple services and a database to size, upgrade and monitor |

## Questions to ask on any ticket

1. **Cloud or self-hosted?** It changes who can see server-side logs and metrics, and who can fix server problems.
2. **Which versions?** Server, CLI and SDK versions matter. Many tickets turn out to be version mismatches or fixed bugs.
3. **Where does their code run?** Kubernetes, serverless, VMs: it changes how deploys, scaling and networking work.

> **🎧 Support angle**
> At an early-stage company, support often spans both the managed service ("our cloud environment is slow") and self-hosted users ("our cluster won't start after upgrading"). Get these three answers at the start of every ticket. They save a round trip later.
